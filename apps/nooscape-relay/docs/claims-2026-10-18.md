# Claim this agent: the server (C1), the page (C2) and the history (C3)

The owner of an agent on an EVM ERC-8004 registry signs one message with their wallet, the server checks that the registry says that wallet owns the agent now, and the owner may then write a name, a website, a description and a few links beside what Nooscape observed. This is stages C1 to C3 of the plan (`AUTO_REVIEW_PLAN.md`, "Claim this agent"): C1 is the server, the three tables and the daily check; C2 is the Claim button, the wallet connection and the edit form on an agent's page; C3 is what the owner wrote and the public history, shown on the agent's page, with the operator's tool to hold a claim and remove text.

**Status.** C1 is merged, live and verified (PR #150, main b213f39, 18 Oct 2026), and migration 0042 is run (the operator said so on 18 Oct 2026). C2 is merged and live (PR #151, main 3ef7c43). C3 and the wording of the Privacy and Terms pages are merged and live (PR #152, main 52b4a49, merged 2026-10-19 00:01 UTC). The panel shows only when a build names `claims` in `VITE_FEATURES`, and the live build does (checked 2026-10-28; see "Before the page is switched on" for the checks that came first).

**Decided by the operator, 2026-10-18** (record: `docs/approvals/2026-10-18-claims.md`): start the claim flow; add `@noble/curves` and `@noble/hashes` and nothing heavier; C1 covers the Robinhood Chain and BNB Smart Chain registries first, with Solana as a later stage.

## What a claim is, and is not

A claim is the owner's own word, shown beside what Nooscape observed and never in its place. It is **not** a tier, a review, a rating or a score. It does not change whether an entry is listed, its order, its place on the map, any count, or the reviewed records. The flow cannot write any of those: the edit accepts four fields and a strict schema refuses a fifth, and a test fails if the claim code names a tier, a state, a listing flag or a score. The page, when it exists, says "Claimed by the owner wallet; claims are self-described and unverified beyond wallet ownership".

## The flow

1. **`claim.nonce`** (public). The caller names an entry, a wallet and an action (`claim` or `edit`, with the edit for an edit). The server checks the entry can be claimed and answers with the message to sign and when it expires. It asks no chain. Only the SHA-256 of the nonce is stored.
2. **The wallet signs** the message (`personal_sign`). No transaction, no gas, no approval.
3. **`claim.verify`** (public). The server loads the nonce, rebuilds the message from what it stored when it issued it, and requires the text it is sent to be that message byte for byte. It checks the signature, asks the registry who owns the agent now, applies the fleet rule, and only then writes the claim, using the nonce in the same transaction.
4. **`claim.edit`** (public). The same for one edit. The message shows the edit itself, written out as JSON, so the wallet shows what the owner is signing for and a nonce for one edit cannot be spent on another. The registry is asked again before anything is written.
5. **Every day**, a worker step asks the registry who owns each claimed agent that has not been asked in 23 hours (at most 25 a run). A claim whose agent has changed hands is revoked and the history says so.
6. **`claim.freeze` and `claim.unfreeze`** (operator only). A claim on hold cannot be edited and nobody else can claim the agent.

## The message

An EIP-4361 ("Sign-In with Ethereum") message, so a wallet shows it as a sign-in and compares its domain with the page that asked:

```
nooscape.si wants you to sign in with your Ethereum account:
0x7E5F…Bdf

Claim this agent on Nooscape. This only proves you own the wallet. No transaction, no gas, no approval.

URI: https://nooscape.si/agents/<entry id>
Version: 1
Chain ID: 4663
Nonce: <32 hex characters>
Issued At: 2026-10-18T20:00:00.000Z
Expiration Time: 2026-10-18T20:10:00.000Z
Resources:
- eip155:4663:0x8004A169FB4a3325136EB29fA0ceB6D2e539a432:7
```

It binds the site, the page, the chain, the registry and the token, the nonce, and the two times. For an edit the statement ends "Changes: " and the edit as JSON, for example `{"website":"https://example.org/","links":["https://example.org/docs"]}`: the fields it names, in a fixed order, so a wallet shows the website and the links being approved and not a hash of them. (JSON has no line break in it, which an EIP-4361 statement may not have, and the text of each field was cleaned of line breaks before.) A signature made for another site, another agent, another edit or an older nonce is not valid here. The server builds the message itself and compares what it is sent, so there is no parser to get wrong and no way to smuggle a different message past it.

## What the server checks

| Check | Where |
|---|---|
| The nonce was issued by this server, is unused, has not expired (10 minutes), is for this action, and the message is exactly the one issued | `claims.ts` `loadIssued`, and the use is enforced again in the write transaction |
| The signature is the wallet's: 65 bytes, recovery 27, 28, 0 or 1, the low half of the curve for `s` (so a signature has one form), recovering to the address in the message | `claimsCrypto.ts` |
| For a contract wallet (a Safe, say): EIP-1271 `isValidSignature(hash, signature)` on the wallet, only when the address has code | `claimsChain.ts` |
| A counterfactual (EIP-6492) wallet | refused with a clear message; not supported yet |
| The registry says that wallet owns the agent now (`ownerOf`, at `latest`), at the claim and again on every edit. An empty answer is an outage, never "no owner"; only a revert or the zero address is. Before a claim is ended the registry is asked twice, and both answers must say it is not the claimant | `claimsChain.ts` `readOwnerOf`, `claims.ts` `ownerBeforeRevoking` |
| Neither the wallet nor the wallet the entry was registered by is a fleet: 50 or more listings (`FLEET_MIN`, the Noosphere's number), and the wallet holds fewer than 50 claims in force. Counting the registering wallet closes the way round it by moving an agent out of a fleet to a fresh wallet | `claims.ts` `refuseFleet` |
| The entry can be claimed: visible under the public rule, on the Robinhood or BNB registry, with a key that names exactly that chain's registry | `claims.ts` `claimTargetOf` |
| The edit: four fields, sized and shaped (name 120, website 300, description 1,000, five links of 300), https only, no credentials, no address literal, no local name; too long is an error and not a cut | `shared/claimProfile.ts` |

An unreadable chain is "try again", never a verdict, and does not spend the nonce. A verification that fails because of what the caller sent (a signature that is not the wallet's, a wallet that is not the owner, a counterfactual wallet, a held or missing claim) spends the nonce, so a failed attempt costs a new message and a flood of them cannot spend the chain budget for free. The owner changing is a verdict: the claim is revoked and the new owner may claim fresh. Two messages for the same owner signed one after the other make one claim.

## Limits

- 20 requests from one client in ten minutes (before any work; the router calls the same limiter the rest of the site uses).
- 5 messages for one wallet from one client in ten minutes. The wallet is only half of the key: someone who names another person's wallet spends their own allowance and never the owner's, and a request for an entry that does not exist costs nothing.
- 20 edits for one agent in a day, counted from the nonces that made an edit (a refused attempt is not an edit), before any chain is asked.
- Chain reads for a visitor's request: 60 a minute for each chain. Past that the read is refused as "try again" and never queued, so a flood of requests cannot take the compute units the worker shares. The worker's own daily check is not held to it.
- The daily check: 25 claims a run, one or two chain reads each, BNB reads through the same compute-unit bucket as the worker's own reads, Robinhood reads with no retry ladder.

The claim code writes no log line that carries an address or a wallet (a test holds this, and another captures the console while a claim, a refusal, an edit and a failed check run), so the Privacy page's statement about what the server logs stays true. The daily check's own error line drops a driver error's parameters.

## The tables (migration 0042, manual)

`agent_claim_nonces` (the hash of each nonce, used once, with its times as unix seconds so no database session time zone can change the text of a message, the edit it shows, and whether it made a claim or an edit or was spent by a failed attempt; the worker's daily step sweeps rows two days after they expire), `agent_claims` (one claim in force for an entry, enforced by a unique key on `inForceEntryId`, which is null once a claim is revoked), and `agent_claim_edits` (the public history, append-only, ordered by an `AUTO_INCREMENT` `seq` because a timestamp is only to the second). No foreign keys, no ALTER of a live table, no TEXT column. No code updates or deletes a row of the history, and only `server/claims.ts` writes the three tables; tests fail otherwise.

**The migration (0042) is run by hand.** The boot runner skips it (`MANUAL_MIGRATIONS` is `[36, 37, 38, 39, 40, 41, 42]`). Until it is run every claim procedure answers "Claims are not available right now", the daily check does nothing and says nothing, and no page changes.

**To run it.** Paste `drizzle/0042_agent_claims.sql` into the host's SQL console, on the production database, and run it. Then record it:

```sql

```

**To check.** `SHOW TABLES LIKE 'agent_claim%';` shows three tables, and `SELECT * FROM nooscape_schema_migrations WHERE version = 42;` shows the record.

## The independent review

A read-only security review of the finished code (a separate agent that was given the files and a threat model, not my conclusions) found no way to claim or edit an agent without owning it: the signature checks, the binding between message and nonce, single use of a nonce and the ownership read held. It found four ways to abuse the flow and several smaller gaps. All were checked against the code and fixed before this was committed:

| Finding | What it was | What changed |
|---|---|---|
| Medium: lock a wallet out | The limit on messages was keyed on the wallet alone, so anyone could use up an owner's allowance by naming the wallet, even with an entry that does not exist | The key is the wallet and the asker; an unknown entry is refused before anything is counted |
| Medium: free chain spend | A failed verification did not spend the nonce, and every failure cost up to three chain reads on a client the worker shares | A caller's failure spends the nonce; a visitor's chain reads are held to 60 a minute for each chain and refused rather than queued; the worker has its own call |
| Medium: the fleet rule | It counted the wallet claiming, so an agent moved out of a fleet to a fresh wallet passed | It also counts the wallet the entry was registered by, and caps the claims one wallet holds at 50 |
| Medium: an edit message showed only a hash | A phishing page could ask the owner to sign an edit whose content the wallet did not show | The message shows the edit as JSON |
| Low: an edit landing on a claim put on hold a moment earlier | A read and a write with nothing between them | The write is conditional on the claim being active and in force, and the nonce is used in the same transaction |
| Low: a trailing dot in a link's host (`localhost.`) | The parser keeps the dot, so the local-name rule missed it | A host ending in a dot is refused |
| Low: ambiguous chain answers could end good claims | A revert was recognised by loose wording ("invalid token" is also a bad-key message) and an empty answer meant "no owner" | A revert is the EVM's own words or JSON-RPC code 3; an empty answer is an outage; two agreeing answers are needed before a claim is ended |
| Low: the nonce table grew without limit and the edit count had no index | | A covering index, and the daily step sweeps rows two days after they expire |
| Info: a log line could carry a driver error's parameters | | The daily check's error line drops them |
| Gaps in the tests | A hash was checked by the same code that made it; an assertion that could pass without asserting; a router test that did not check the code; nothing for an edit racing a hold, for a fleet transfer, or for what is actually logged | A fixed external value (the well-known hash of "hello world"), real assertions, the codes, and a test for each other gap |

Also done because of the review: the nonce times are unix seconds, so a database session's time zone (and a daylight-saving change) cannot change the text a message is rebuilt from.

**Still to check or decide, not changed here:**

- **The trusted proxy count.** The per-client limit uses `req.ip`, and `server/_core/index.ts` trusts one proxy hop. If the host's network puts one more address in front of the app, every visitor would share one client key and one visitor could use up the 20 requests for everyone. The operator console's client-address check shows what the server sees; check it before the page ships.
- **Owner-written text on a page (C3).** It is cleaned of control and invisible characters and is not HTML-escaped. When a page shows it: render it as text and never as HTML, escape it for any server-side meta tag, and give a link `rel="nofollow ugc noopener noreferrer"`.
- **A stale claim.** A transferred agent keeps its claim until the next daily check, and the check runs on ticks that claimed sources, 25 claims a run. The page should say when the owner was last checked (`lastOwnerCheckAt`).
- **A genuine buyer of an agent minted by a fleet** is refused under the registering-wallet rule. That is a policy call: a buyer can claim once the directory's count for the fleet's wallet changes, and fleet-level claims are not built.
- **One of the mutation checks is redundant on purpose:** the conditional write for an edit is a second layer behind the status check inside the same transaction, so removing it alone is not caught.

## The page (C2)

**Where.** A "Claim this agent" section on the page of an acknowledged entry on the Robinhood Chain or BNB Smart Chain registry, between "Owner" and "Host and links". No other entry gets it (a Solana entry, a reviewed record), and the server decides: `claim.state` says whether the entry can be claimed.

**The switch.** `VITE_FEATURES=claims` at build time (`shared/features.ts`, the same switch the Watch and Patrols pages use; see `docs/watch-patrols-scaffold-2026-10-15.md`). A build without it renders no section and makes no call to the claim API; the default build was checked in a browser for exactly that. The panel also hides itself while migration 0042 is missing (`claim.state` answers "not available").

**What the panel shows**, by what the server says and which wallet the visitor connected:

| State | Shown |
|---|---|
| nothing claimed | what claiming asks and costs (one signature, no transaction, no gas, no approval, no access to funds), what a claim is (the owner's word, not a review, a tier or a score), a "Connect a wallet" button |
| claimed, any visitor | "Claimed by the owner wallet 0x1479…9325. Claims are self-described and unverified beyond wallet ownership.", when the registry was last asked who owns the agent, and a "Hold this claim? Connect your wallet" button |
| claimed, the holder connected | the same lines and the edit form: name, website, description, links, filled in with what the owner wrote |
| claimed, another wallet connected | "The connected wallet is not the one that holds this claim." and no form |
| on hold | "This claim is on hold." and nothing else |

**The wallet.** `client/src/lib/wallet.ts` finds wallets the way browsers expect (EIP-6963, then the older `window.ethereum`), asks for an account with `eth_requestAccounts` and for one signature with `personal_sign`, and nothing else; every request goes through one function that refuses any other method. It does nothing until a visitor presses a button, so a page that never offers a claim never touches a wallet. Solana wallets are not offered: the server reads EVM registries only. A test fails if any client source names a transaction, signing or wallet-management method, if anything but `wallet.ts` reads `window.ethereum` or sends a request to a wallet, or if the panel is imported anywhere but the entry page.

**The message is shown before it is signed.** After "Claim this agent" or "Review the change" the whole message appears in the page, under "This is the whole message your wallet will show you. It only proves you own the wallet. No transaction, no gas.", and only then is "Sign in your wallet" offered, with Cancel. Just above the button the panel says "By claiming you agree to the Terms for claiming. What Nooscape keeps is on the Privacy page.", each a link that opens in a new tab so the message on screen is not lost. An edit's message carries the change as JSON, so the visitor sees what is being signed for. The browser check confirmed that the text the wallet signed is the text the page showed.

**The edit form** names only the fields that changed (an emptied field becomes a clearing edit), cleans and checks them with the same rules the server holds them to, and shows a refusal beside the field. Nothing changed is not an edit. The server decides.

**What it keeps.** Nothing. No `localStorage`, `sessionStorage`, IndexedDB or cookie, nothing in a URL, nothing in the console; the connected account lives in the component and goes with the page. A reload shows the claim and asks the visitor to connect again before the form returns. A test holds the claim client code to this, and the browser check read the storage after a full flow (only the owl choice the script itself set).

**What it says when something goes wrong**, in plain words: a wallet refusal is "You declined in your wallet. Nothing was signed."; an open request in the wallet says to answer it; the server's own fixed sentences are shown as they are ("The registry does not record that wallet as the owner of this agent. Start again for a new message."); anything else, including text shaped like data, becomes "That did not work. Try again in a few minutes." The wallet's own error text is never shown. A message that failed its checks is spent, so the page drops it and the visitor starts again.

**`claim.state`** (public query, strict input) is new in C2. It asks no chain and writes nothing, reads one row by an indexed key, and answers whether the entry can be claimed and the claim in force, with what its owner wrote. It never returns a signature or its digest. It is public like the rest of the API, so what an owner writes can be read by anyone who calls it; the page does not show it to other visitors until C3 decides how (render as text, links with `rel="nofollow ugc noopener noreferrer"`).

**Accessibility.** The status and error lines are live regions, the form fields are labelled with hints and `aria-invalid`, the form is locked while a message waits to be signed, and focus moves to "Sign in your wallet" when the message appears.

**Checked in a browser.** A real production build against a real database, a fake chain (it answers `ownerOf` from a file, so the check can see what the server asked) and a fake wallet that signs with a real key, at 1440 and 375 pixels wide: claim, refused edits, an edit of four fields (the history holds the claim and one row for each field, and the registry was asked at the claim and again at the edit), the same page after a reload, a second wallet that is not the holder, a refusal in the wallet, a wallet the registry does not list, a claim on hold, a BNB entry, a Solana entry with no panel, no console error and no horizontal overflow, nothing kept in the browser, only the two wallet methods asked, and no request to a host other than the site and its analytics. The same page in a default build shows nothing.

## The history and what the owner wrote (C3)

**What a visitor sees**, inside the same "Claim this agent" panel and so behind the same switch:

- **What the owner wrote.** For a claim in force and not on hold: the name, the website, the description and the links, under "What the owner wrote" and "Written by the claim holder. Nooscape has not checked it, and it does not change how this entry is listed." It sits below "Claimed by the owner wallet" and never in place of the entry's own name or facts. Everything is text. A website or link is a link only when it is an https address, opens in a new tab and carries `rel="nofollow ugc noopener noreferrer"`; anything else is plain text. Markup written into a field (a browser check wrote `<b>` and `<script>` tags) is shown as the words it is, and runs nothing.
- **The claim history**, a closed section that counts its entries and, when opened, lists every claim, edit, hold, end and removal for the entry, newest first (the 100 newest, saying so when there are more). Each row has the time; a claim or an edit has the signing wallet and the start of the signature digest; an edit shows what was set, changed from and to, or cleared. A claim that ended says why in words ("The registry shows a new owner."). The history is shown for an entry whose claim ended, too.

**What the server sends.** `claim.history` (public query, strict input; no migration) returns, for each row, only the kind, the field, the old and new text, a `withheld` flag, the signing wallet and digest (claims and edits only), a fixed reason word, the time and its order number. It sends no row id, no claim id, no entry id and no signature, and no wallet on a hold or an end (on an end the stored wallet is the new owner's, who did not sign it).

**A hold hides the text.** While a claim is on hold, `claim.state` returns it with no text and `claim.history` returns each edit without its text and with `withheld` true. The text stays in the table and comes back when the hold is lifted. The page shows "This claim is on hold." and nothing the owner wrote.

**Removal.** `claim.removeText` (operator only, strict input) clears a claim's current text for the fields named, and adds one `redact` row per field to the history. It also takes who asked, `owner` or `nooscape`, which the row keeps as a fixed word (`owner_request` or `nooscape`): the public history says "Removed the name from view at the owner's request" or "... by Nooscape", and never why, because a reason would expose a reporter or republish a complaint. Every edit of that field before the row then comes back from `claim.history` as `withheld` without its text, and a later edit by the owner is a later row and shows. It works on a claim in any state, an ended one included. Nothing in the history table is changed or deleted: the full text stays in its rows, which is the private record, and a test holds that rows already written are identical after a removal. The legal review's rule, accepted by the operator, is that the public history shows that a change was made and not what it said once the text is removed.

**The operator's tool.** A "Claims" section at the end of the operator page (`/admin/sources`, signed in only): paste an entry's id or the address of its page, see every claim ever made for it (status, wallet, id, text), put one on hold or take it off, and remove the checked fields from view. A removal needs the operator to say who asked (the button waits until it is said) and asks to confirm. It calls `claim.operatorClaims`, `claim.freeze`, `claim.unfreeze` and `claim.removeText`, all operator-only; a request without the operator's session is refused with 401.

**Deviations from the plan.** The plan's C3 is "front end plus one read endpoint". It has two more server procedures and an operator screen, because the legal review asked that removal and a hold that hides text be real before the pages promise them. No migration: `kind` is a `varchar` and a removal row is `kind = "redact"`.

**Checked in a browser** (a production build, a real database, a fake chain, a fake wallet signing with a real key, 1440 and 375 pixels wide): an owner claims and writes four fields, one holding markup; a visitor sees the text with the right labels and links and no markup run; the history counts, opens and shows who signed; the operator signs in with a scratch token, finds the claim from a page address, puts it on hold (the page and the API show no text, the history keeps the edits and shows they are withheld), takes the hold off (the text returns), removes the name (it leaves the page and the history shows only that a change was made; the table still holds it and gained one removal row), the owner writes a new name (it shows) and, with the registry showing a new owner, an edit by the old owner revokes the claim, the page offers the claim again and the history says the claim ended and why. A request to the operator's procedures without a session is 401. The operator's card was clipped at phone width in the first run and was fixed, with a check that nothing in it is wider than the card. The default build shows nothing and makes no claim call, the history included. The C2 flow was run again on this build and passes.

## From the legal review (built in C3)

The legal review of 18 Oct 2026 asked for four things, and the operator accepted its history model. All four are built in C3:

- **The public history shows that a change was made, not always what it said.** Date, field and signing wallet, and old values unless removed; a removal is a new `redact` row, never an update; the full rows stay as the private record.
- **A way for the operator to remove an owner's text from view.** `claim.removeText` and the operator's Claims section.
- **A hold hides the text, not only blocks edits.** In `claim.state` and in `claim.history`.
- **An ended claim says so.** The history row "The claim ended", with the reason.

The Privacy page gains the history sentence the review said must ship with the display ("If something in it is removed from view, the history shows that it was removed, not what it said"), and the Terms say nothing is shown of a claim on hold. Both go back to the operator's legal assistant (the v3 note).

**Second round (the review of the v3 note, 2026-10-18).** The assistant kept the digest (Q1), asked for an actor word on a removal and not a reason (Q2, built: `owner_request` or `nooscape`), found an ended claim keeping its history consistent with two provisos (Q3: the removal route is not for a current holder only, and the Privacy section says so), and kept "without advance notice" (Q4). Wording applied: "the start of a digest of its signature", "the newest 100 changes are shown", the hold clause in the history bullet, and the end-of-claim bullet restored (what you wrote is no longer shown as the owner's text, the history stays with the text unless removed, and removal can still be asked for). Not applied: "or if Nooscape ends it under the Terms", because no operator action ends a claim today; the operator's tools are a hold and a removal. The Terms still say Nooscape may end a claim, which is a power it does not yet have a tool for. What an owner wrote is readable by anyone through the API from the moment it is saved, and the page now shows it.
