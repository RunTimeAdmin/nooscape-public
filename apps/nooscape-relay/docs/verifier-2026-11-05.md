# The verifier: one check, three ways to run it (2026-11-05)

> **Status:** Built 2026-11-05 on the owner's order, from the second outside architecture review of that day (its feature F2: a public verifier that other people's systems can depend on). The package was published to npm as `nooscape-verify` 0.1.0 by the owner on 2026-11-05 (see the end).

## What there was, and what was missing

A reviewed record's signed packet (the file the "Export signed JSON" button saves) could be checked in one place, the site's `/verify` page through the tRPC procedure `atlas.verifyEvidence`. The keys it is checked against were already published at `/.well-known/nooscape-keys.json` (active, retired and revoked, as [the rotation record](./evidence-key-rotation.md) describes). What was missing was a way to check a packet without the website or its page: something a gateway or a marketplace can run in its own code and on its own machine, and a plain HTTP form for those that cannot.

## What was built

1. **The check, in one file.** `verifier/src/verify.ts` holds the check that used to live inside `server/routers.ts`: the SHA-256 digest of the canonical payload, the Ed25519 signature over it, the displayed fields rebuilt into that payload byte for byte, and the key looked up in a key list. The body was moved without a change of meaning. Every string literal and every line of logic was compared with the original; the differences are the function's signature, the key list now passed in instead of read from the relay's environment, a constant for the payload version, and two renamed imports. Its one dependency is Node's own `crypto`. `server/evidence.ts` now takes its key matching and its retirement rule from the same file, and `routers.ts` calls it.
2. **`POST /api/v1/verify`.** Free and keyless. The body is a packet; the answer is the check's result under the API's names (`valid`, `verified_by_nooscape`, `hash_valid`, `signature_valid`, `payload_matches_envelope_fields`, `key_status`, `issues`, and the rest) with a statement of what it shows and does not. It uses the public limit of 30 requests a minute from one address and is not for sale: past the limit it is limited (429), never offered for a payment. A body is at most 512 KB, is read and dropped, and is not stored, logged or cached. A key's request is counted under the name `verify`. It is in the OpenAPI document, the index and the `/developers` page.
3. **The `nooscape-verify` package** (`verifier/`). A command, `nooscape-verify packet.json --keys nooscape-keys.json` (or `--fetch-keys`), and a library (`readPacket`, `readKeyManifest`, `verifyEvidencePacket`, `findKey`). No dependency, ESM, Node 18 or later, built with `tsc`. It makes no request unless `--fetch-keys` is given, and then only over https. Exit status 0 verified, 1 not verified, 2 input that could not be read.

There is one source. The package is built from this folder and there is no second copy, because the copy of the MCP package that once sat in `packages/` fell behind its repository and had to be removed (27 October).

## How the three agree

They run the same function, so they cannot disagree about a packet's key, its digest or its fields. The one place they could differ is how each reads a packet before the check: the tRPC procedure and the REST endpoint through the relay's schema (`server/evidencePacketSchema.ts`, moved out of `routers.ts` unchanged), the package through `readPacket`. Both drop fields the packet does not define and rebuild the rest in the order the relay signed it, which is what lets a reordered copy of a genuine packet still verify. `server/evidencePacket.test.ts` holds them to the same answer: the same inputs accepted, twenty damaged ones refused by both, the same packet out byte for byte, and the same result through the schema, the reader and the tRPC procedure. It also reads the key list the relay really publishes with the package's reader and checks a packet signed by the relay's own key against it.

## What the check shows, and what it does not

It shows that a packet is unchanged since a key signed it, and where that key stands in a list: active, retired and the packet dated up to the day of retirement, revoked, or not in the list. It says nothing about the agent the packet is about, and the statement in every answer says so.

- The key list is the root of trust. The command trusts the list it is given; `--fetch-keys` trusts the https connection to `nooscape.si`, and a person who needs more saves a copy and uses `--keys`.
- The retirement date is inside the packet, so the rule guards against mistakes and not against a leaked key. A leaked key is stopped by marking it revoked, which the check refuses.
- A packet with no key id cannot be matched to a published key, and is reported as such.
- Nothing is checked about what the entries say. They are what Nooscape recorded.

## Checked

- `verifier/src/verify.test.ts` (49 tests): the check against real Ed25519 signatures made with Node's crypto (active, retired before and after the date, revoked, an unknown key, a key id that matches with someone else's key, every way a packet can be changed), a packet signed with an attacker's own key that borrows the relay's key and key id in the envelope (refused against an active and a retired key alike), the key helpers, the packet reader (sixteen refusals, each naming the field) and the key list reader (every kind of bad line named and left out).
- `verifier/src/cli.test.ts` (15 tests): the command with a made-up disk, input and network, and `verifier/src/package.test.ts` (5 tests): the package compiled with its own tsconfig into a temporary folder holding its real `package.json`, and the built command and library run from there.
- Against production on 2026-11-05: four reviewed records' real packets, fetched from the live site, verify with the built command and the key list fetched from `nooscape.si` (exit 0, the key active). For those four and a changed copy of each, the eight answers are identical, field for field, to what the deployed site's `atlas.verifyEvidence` gives for the same packet. That is the old code and the new check agreeing on real signatures, not only on packets made for tests.
- `server/evidencePacket.test.ts` (4 tests), and the existing key rotation and verification tests, which assert the old behaviour through the old entry points and pass unchanged: `keyRotation.test.ts`, `keyRotationVerify.test.ts`, `evidence.test.ts`, `keyList.test.ts`.
- The route: `apiV1.test.ts` (free and keyless, tampered and unknown-key packets, the key list read only for a packet that names a key, a body that is not a packet refused with the field named and never repeated, POST only, JSON and size limits, the shared public limit, a key's request counted as `verify`), and `apiV1Payments.test.ts` (free while pay per call is on, never offered for a payment). Two design guards in `apiV1.test.ts` that said "two POSTs" now say three.
- Thirty-eight planted bugs across the check, the readers, the command, the route and the document, thirty-five of them caught by a test. The other three are equivalent: each removes one of several places that enforce the same rule (the signature or the wrapper key counted again in `valid` or in the authorship flag, where an issue or the key test already refuses it), so the answer cannot change. Three of the first run were not caught and led to tests: a digest changed alone, a refusal that repeated the start of the body, and the forged wrapper key above.

## Published

The owner published `nooscape-verify` 0.1.0 to npm on 2026-11-05 at 21:20Z with `npm publish` from a clean export of this folder (a checkout with Windows line endings would not make the same tarball). The registry lists 10 files, 38,755 bytes unpacked, `latest` set to 0.1.0, and a tarball SHA-1 of `2608d022f1fd5d8c6dfc8038a6c2457b2ae36c94`, the same as `npm pack --dry-run` gave before the publish. Before the publish the registry had answered 404 for the name. It also lists a `0.0.0-stage` version, described as a temporary placeholder for staged publishing (2 files, 337 bytes), published under the same account a minute earlier; `latest` does not point at it. Run from the registry copy, the sample packet verifies (exit 0) and a copy with one letter changed is refused (exit 1). The README is part of the package and a published version cannot be edited, so it carries no "not yet published" line. A version number is used up once it is published: a fix goes out as 0.1.1. The package's `repository` points at the public mirror (`apps/nooscape-relay/verifier`), which carries this folder only after its next refresh, so that link does not resolve until then. The package has no LICENSE file (its `package.json` says MIT). A Python port (the review mentions PyPI) is not built.

## Rolling back

Remove the route, its spec entry and the `/developers` card; the package folder stands alone and nothing in the relay depends on it. The published package stays on npm either way and is retired with `npm deprecate`. The move of the check out of `routers.ts` is covered by the tests above.
