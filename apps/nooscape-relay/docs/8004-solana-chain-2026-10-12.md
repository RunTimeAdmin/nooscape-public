## 2. The verified AgentAccount layout

Fixed 748-byte Anchor accounts, discriminator `f177458ce9097032`: collection [8..40), creator
[40..72), **owner [72..104)**, **asset [104..136)**, bump, atom_enabled, then a borsh `Option<Pubkey>`
for agent_wallet (None = one `0x00` tag byte, Some = tag + 32), three reputation windows (digest +
u64 count each — skipped, not decoded; the ratings surface is a later workstream), a parent_asset
Option, two lock bytes, and three u32-LE-length Strings: agent_uri, nft_name, col.

Two probe findings shaped the adapter:

- **The Option arithmetic is the layout.** The first layout guess assumed both Options were Some
  (a fixed 326-byte prefix); the discovery run showed name markers at variable offsets. The real
  prefix is 262 + 32·(wallet Some) + 32·(parent Some). The decode walks the tags and fails closed
  on any tag > 1.
- **Bytes past col are stale Anchor padding residue, not a field.** In-place rewrites never zero
  padding, so 7 of 1,504 live accounts carry ASCII suffixes of prior field values (an old URI tail,
  an old `"Agent"` name with its length header, `gent` fragments) at shifted offsets. The decode
  scans the tail for non-zero bytes, counts `tailResidue`, and never parses it — the three-string
  layout is complete.

Display names come from the URI's inline JSON (`data:` URIs, base64- or percent-encoded, and the
raw JSON object literals some registrants write into the field), decoded locally — no dereference,
no execution. A future non-placeholder nft_name beats the synthetic fallback
(`8004 agent <asset prefix>`); the inline name always wins. `locatorHost` comes from an `https://`
URI's hostname, lowercased.

## 3. State diff with disappearance-based closure

The 8004 program has no event surface to sweep, and the AgentAccount carries every chain fact
inline — so, like the Metaplex pass, change tracking is a **state diff**: one `getProgramAccounts`
scan of the whole program, decoded strictly, diffed against the source's own directory rows.

- **register** — live account whose asset has no prior row; also a live account reappearing after
  an acknowledged closure (a fresh registration of the same asset: the live upsert clears the
  marker and returns the row to public reads).
- **transfer** — prior registrant non-null and the owner changed. A null-registrant prior was
  never chain-acknowledged: full chain state adopted silently.
- **profile_update** — displayName or **locatorHost** changed. The URI edit is the 8004-specific
  profile signal: a registrant editing their registration URI rewrites the host the directory
  shows, so the diff needs the prior row's locatorHost (`listAgentDirectoryEntriesForSource` now
  returns it).
- **asset_closed** — a prior row whose asset is **absent from the enumeration**. The account itself
  is gone; the asset pubkey is the only address that outlives it.

Closures are **hide-once** (the 0023 marker): the first observation marks the row closed keeping
its last name and owner, later passes skip it without an event, and acknowledged closures can
never consume the per-pass event cap. A closure whose asset has **no successful transaction at
all** is still a real disappearance: the row is marked closed, but the ledger only records honestly
anchored events, so it is counted (`unanchoredClosureCount`) and never ledgered.

**Attribution asymmetry.** A live change attributes to the **AgentAccount PDA** — the transaction
that made the change touched it — and a live change with no successful transaction **fails the
pass** (a state we observed must have a cause). A closure attributes to the **asset pubkey** and
may proceed unanchored per above. One paced `getSignaturesForAddress` (limit 5) per event-bearing
address, in the diff's deterministic order.

**Fail-closed decode.** Length ≠ 748, wrong discriminator, Option tag > 1, and per-string bounds
all fail the whole pass. The gPA envelope is stricter than the Metaplex parser: an entry without a
pubkey + base64 data tuple **throws** instead of being counted — under disappearance-based closure
detection, a misread envelope could hide a live account and masquerade as a closure. (The Metaplex
§9 incident is the standing reminder of what a lenient parser can manufacture.)

## 4. Divergences from the Metaplex pass, by design

- **The pass owns locatorHost.** The Metaplex upsert runs `preserveLocatorHost` because its API
  pilot rows carry a host the chain pass must not null; 8004 has no API path — the registration
  URI *is* a chain read, so a URI edit rewrites the host honestly. No `preserveLocatorHost`.
- **No observe mode.** One runner mode: the chain pass. Observe/backfill/registrants are rejected
  server-side with a clear message; the console exposes only **Run chain pass**.
- **Closure marker list from the adapter, not re-derived from events.** `closedExternalKeys`
  covers anchored and unanchored closures alike; the runner marks exactly that list.
- **Cursor `s8004:<slot>`.** Only an `s8004:` cursor counts as a completed inventory; absent,
  empty, and foreign cursors seed (a re-inventory is always safe: upserts only, zero events).

## 5. Pass anatomy, cost, and storage

One pass = `getSlot` + one program `getProgramAccounts` (748-byte accounts, ~1.1 MB at current
scale) + one signature scan per event-bearing address, paced 1.2 s (`SOLANA_RPC_PACING_MS`), through
the shared `solanaRpc.ts` client — 30 s timeout, 16 MiB cap, short retry ladder, `ENV.solanaRpcUrl`
(the operator's keyed Helius endpoint; never in a source row). Growth past a 4,000-AgentAccount
ceiling stops the pass loudly. At most 25 events per pass; overflow defers whole accounts (neither
evented nor upserted) so stale prior state re-diffs next pass — lossless by construction. The whole
snapshot, including every attribution, completes before anything is written; ledger writes are
INSERT-IGNORE'd on `(sourceId, transactionSignature, externalKey)`.

**Enum-only migration 0024** — no new table, no new column. The pass reuses
`agent_directory_entries` (externalKey = the agent asset pubkey — the same key space Robinhood
cross-chain registrations resolve, which is what makes the planned cross-chain linking a join and
not a guess), the per-source `agent_solana_activity` ledger (0021), the generic run/observation
tables, and the `assetClosedAt` hide-once marker (0023). `registrant` is already varchar(64) (0021).
Three idempotent protocol-enum MODIFYs add `solana_8004` ahead of `usdg_settlement` (MySQL re-maps
enum values by string, so the mid-list insert renumbers nothing), self-applied at boot before traffic.
