# Discovery files for the API and pay per call (21 October 2026)

Status: built, with the checks below. Three small additions that let a model, an x402 client or an indexer find out what the API is and how to
call it and pay for it, without reading the developer page: `/llms.txt`, `/.well-known/x402`, and a Bazaar block in every 402. No migration, no
new setting, nothing to switch on. A price, the receiving address or a served chain that changes in the settings changes in all three.

## Why

The monetization review of 21 October found that x402 on Arc had taken one payment ever, the operator's own test of $0.01, and that nothing
outside Circle's Agent Marketplace form tells an agent we exist. The 402 carried `extensions: {}`, so a client that read it learned the price
and nothing about how to make the call. The operator asked for the files the same day.

## What it adds

1. **`/llms.txt`** (`server/discovery.ts`, `llmsText`). Plain text in the llms.txt layout: a title, a summary line that says what Nooscape is and
   is not (no score, rating or verdict), then the documents, the endpoints, the chains, the key tiers, the payment terms and the API's own
   statement. It is a rendering of what `/api/v1` already serves (`indexAnswer`), so the endpoint list, the limits, the chains and the prices are
   not typed a second time. While pay per call is off, paused or not known to be on, the payment section is left out.
2. **`/.well-known/x402`** (`x402WellKnown`). The x402scan discovery format: `{ version: 1, resources: [...], instructions }`, with the one route
   that answers 402 to a caller with no key, `POST /api/v1/check`, as a full address under the resource origin of the 402. While pay per call is
   not taking payments it is a JSON 404, answered by the route and not passed on, because the client's catch-all would send the page with a 200
   and an indexer would read that as a document. If the payment state cannot be read it is a 503 that is not cached.
3. **`extensions.bazaar` in the 402** (`server/x402Bazaar.ts`, used by `termsReply`). The Bazaar discovery extension: `info` says the method and
   an example body (check) or the path parameters (lookup), and `schema` is a JSON Schema that `info` validates against. A client or a validator
   that reads the 402 can build a valid call from it. The lookup's block carries the route template `/api/v1/agents/:chain/:id`.

All three are public, cached for five minutes, open to other sites (CORS `*`, cross-origin resource policy lifted, as the relay key list is), and
hold no secret: the receiving address and the prices are in every 402 already.

## What it will not do

- **It promises no listing.** An indexer decides for itself. x402scan reads the well-known file, but a third party's changelog says it indexes
  Base and Solana and not Arc (not checked here). The Coinbase Bazaar catalogs a route from a payment that settled through the Coinbase
  facilitator, and ours settle through Circle's Facilitator Service, which is also why the block cannot reach a catalog by being forwarded: the
  body we send the facilitator is built from our own terms and carries only the payment identifier as an extension. What the block does is
  describe the route to any client or validator that reads the 402. Circle's Agent Marketplace reads an OpenAPI document or a PDF, not this.
- **The lookup is not in the well-known file.** Within the free limit (30 a minute from one address) it answers 200, so an indexer that probes it
  would record a failure. It is in `/llms.txt`, and its 402 carries a block for the moment the limit is used.
- **No output example and no free text in the block.** The 402's `PAYMENT-REQUIRED` header is the base64 of the body, and a client sends the
  extensions back inside its payment, so each byte is carried three times. Measured on the built server, the 402's header block went from
  about 2.1 KB to 3.2 KB with the block (the header alone grew by 1,060 bytes, to 1.9 KB) and a standard client's payment header is 2.3 KB, against an 8 KB
  limit that an edge may apply to one line and a 4 KB buffer that some proxies use for the whole header block. An example answer would also drift
  from the real one, and the Bazaar refuses a listing whose metadata could be read as an instruction to an agent. The OpenAPI document and
  `/llms.txt` say what the fields mean and what comes back.
- **It changes no term.** A payment is judged on the terms built in `requirements`, and `settleBody` builds what the facilitator receives
  from our own terms. A client that sends back a changed block is served exactly as before (checked, below).
- **No ownership proof.** The x402scan format can carry a signature by the receiving wallet over the origin. No key on this server can sign for
  that wallet, by design, so the field is left out.

## Shape, and how it was made

The two blocks were built with the reference package (`@x402/extensions` 2.28.0, `declareDiscoveryExtension` and the resource server's
`enrichDeclaration`) and the repo's output was compared with it: identical, with one intended difference. The check takes JSON only, so its
schema allows `bodyType: "json"` where the package lists all three. Both validate with the package's validator, and a version with a wrong
method, an agent with no id, a body with two of wallet and url, or no schema is rejected by it, so the pass means something.

The repo has no JSON Schema validator and none was added for this. `server/x402Bazaar.test.ts` pins both blocks exactly and checks the one
property that matters in code, that what `info` says is what `schema` allows. The block is 786 bytes for the check and 618 for the lookup.

## What was checked

- Unit tests: `server/x402Bazaar.test.ts` (the pinned blocks, the fallback for an address that does not read as a lookup, sizes, no prose),
  `server/discovery.test.ts` (the page from the index, the chains that are served, the payment section while on and its absence otherwise,
  prices as set, no secret, no long dash, full https links, the routes with payments on, paused, not recording, not configured and unreadable,
  and that other paths still reach what is mounted after), and `server/x402.test.ts` (the block in the 402, header and body equal).
- The built server on a scratch database, with Circle stood in for and the real x402 client as the buyer: the 30 existing pay per call checks
  (free limit, 402, hostile headers, idempotent retries, a pending, refused and lost settlement, a refused key) all still pass, and 24 new
  ones: the two files, the 402 of the check and of a lookup past the limit validated with the reference validator as served, the real client
  reading a 402 that carries the block, sending it back in its payment and being served, a payment with no extensions served, and a payment
  that sends back a changed block served on our terms.

## After the merge

```bash
curl -s https://nooscape.si/llms.txt
curl -s https://nooscape.si/.well-known/x402
curl -si -X POST https://nooscape.si/api/v1/check -H 'content-type: application/json' -d '{"agent":{"chain":"arc","id":"1"}}'
```

The 402 must still carry `payment-required`, and the response header block should be about 3.2 KB. The operator's earlier $0.01 test payment is
the one that proves a client still pays through the edge. Public validators exist (`api.cdp.coinbase.com/platform/v2/x402/validate`, the
`@agentcash/discovery` command); each sends our address to a third party or runs downloaded code, so they are the operator's call.
