# Discovery files for the API and pay per call (21 October 2026)

Status: merged and live (PR 188, 21 October 2026 17:00Z, main 57bea2d) and checked live afterwards, below. Three small additions that let a model, an x402 client or an indexer find out what the API is and how to
call it and pay for it, without reading the developer page: `/llms.txt`, `/.well-known/x402`, and a Bazaar block in every 402. No migration, no
new setting, nothing to switch on. A price, the receiving address or a served chain that changes in the settings changes in all three. A fourth file,
the root `/openapi.json`, was added later the same evening: see its section below. On 22 October the well-known file gained the standard form and a proof of the
domain was added for a listing at Tolly Labs: see "The standard form, and the listing at Tolly Labs".

## Why

The monetization review of 21 October found that x402 on Arc had taken one payment ever, the operator's own test of $0.01, and that nothing
outside Circle's Agent Marketplace form tells an agent we exist. The 402 carried `extensions: {}`, so a client that read it learned the price
and nothing about how to make the call. The operator asked for the files the same day.

## What it adds

1. **`/llms.txt`** (`server/discovery.ts`, `llmsText`). Plain text in the llms.txt layout: a title, a summary line that says what Nooscape is and
   is not (no score, rating or verdict), then the documents, the endpoints, the chains, the key tiers, the payment terms and the API's own
   statement. It is a rendering of what `/api/v1` already serves (`indexAnswer`), so the endpoint list, the limits, the chains and the prices are
   not typed a second time. While pay per call is off, paused or not known to be on, the payment section is left out. The check's line in the endpoint list
   follows the same switch (from 22 October 2026): with payments on it reads "Needs a Pro key, or $0.01 a call with no key" (the price as set), and otherwise "Needs a Pro key",
   so a page never tells an agent it needs a key where a payment would do, and never offers a payment that is not taken. The keys page and the developer page say the same.
2. **`/.well-known/x402`** (`x402WellKnown`). The x402scan discovery format: `{ version: 1, resources: [...], instructions }`, with the one route
   that answers 402 to a caller with no key, `POST /api/v1/check`, as a full address under the resource origin of the 402. While pay per call is
   not taking payments it is a JSON 404, answered by the route and not passed on, because the client's catch-all would send the page with a 200
   and an indexer would read that as a document. If the payment state cannot be read it is a 503 that is not cached. From 22 October 2026 it carries the standard form
   beside that one (see "The standard form, and the listing at Tolly Labs").
3. **`extensions.bazaar` in the 402** (`server/x402Bazaar.ts`, used by `termsReply`). The Bazaar discovery extension: `info` says the method and
   an example body (check) or the path parameters (lookup), and `schema` is a JSON Schema that `info` validates against. A client or a validator
   that reads the 402 can build a valid call from it. The lookup's block carries the route template `/api/v1/agents/:chain/:id`.

All three are public, cached for five minutes, open to other sites (CORS `*`, cross-origin resource policy lifted, as the relay key list is), and
hold no secret: the receiving address and the prices are in every 402 already.

## The root OpenAPI document (added 21 October 2026, evening)

`/openapi.json` (`x402OpenApi` in `server/discovery.ts`) is the fourth file. AgentCash's discovery specification (https://agentcash.dev/discovery, read
21 October 2026) says x402scan reads the OpenAPI document at `{origin}/openapi.json` first and the live 402 second, and its table does not list
`/.well-known/x402`. The root path was a 404 until now (the whole API is described at `/api/v1/openapi.json`), so a registration at x402scan would have
failed with "OpenAPI not found".

- **What it holds.** One route, `POST /api/v1/check`, as the API's own description of it (`apiV1SpecFor`, so its request, its answer and its words are not
  written twice), and the two fields their discovery reads: `x-payment-info` (a fixed price in decimal dollars from the live setting, `0.010000` today, and
  the protocol `x402`) and `info.x-guidance` (what the route takes and returns, that it gives no score, rating or verdict, and how the 402 works). Only the
  schemas that route reaches are carried, so the document is about 34 KB and not the whole API's. A test checks that every `$ref` resolves. After the specification
  itself was read (Agentcash Discovery v1, in the package `@agentcash/discovery`), three more fields: `security: []` on the route (discovery reads the security
  declaration with `x-payment-info`, and a key there makes the route "key and paid", where payment alone opens it), `info.contact.email` (the specification recommends
  it, and registries use it to verify who runs the origin; it is the address the contact page gives for the API), and `x-agentcash-guidance.llmsTxtUrl` (a pointer to `/llms.txt`).
- **What it leaves out.** The lookup: within the free limit it answers 200, so their probe of it would record a failure, as it would from the well-known
  file. The whole API stays at `/api/v1/openapi.json`, unchanged. Ownership proofs (`x-agentcash-provenance`, `ownershipProofs`) are not built: the specification
  names the field and gives no recipe (see "No ownership proof" below).
- **When payments are off.** As with the well-known file, a JSON 404 of its own (the client's catch-all would answer with the page), and a 503 that is not
  cached if the payment state cannot be read. Both routes now share one function for this (`servePayable`).
- **Probes.** A POST to the check with no body, or with `{}`, already answers 402 (checked live on 21 October), so the failure their documentation lists as
  "Expected 402, got 400" does not apply.
- **The validator and the registration (22 October 2026).** AgentCash's validator downloads and runs code, so running it was the operator's call. It has two commands, and `check`
  takes one endpoint and not the origin (resource identity is origin, method and path): `npx -y @agentcash/discovery@latest discover nooscape.si` lists what the origin offers, and
  `npx -y @agentcash/discovery@latest check https://nooscape.si/api/v1/check` inspects the check. Run on the origin, `check` answers `L3_NOT_FOUND`, which says only that `/` is
  not a resource. Both commands are clean once the output block (below) is deployed. `discover` did not raise `LEGACY_WELL_KNOWN_FOUND` for `/.well-known/x402`, which is still
  served; that runtime no longer reads the file, and it stays until nothing else is known to read it. The operator then registered the API at https://www.x402scan.com/resources/register.
  Seen from outside afterwards, x402scan's page for the receiving address names the origin `nooscape.si` as the seller, on Base through Coinbase (6 transactions, $0.06 and one buyer
  in the past 24 hours when it was read; the page is rendered in the browser, so it was read with a scraper).

## The output block (added 22 October 2026)

The operator ran AgentCash's validator (`discover nooscape.si` and `check https://nooscape.si/api/v1/check`). Both listed the check as paid at 0.010000 USD over x402
and both raised one error, `SCHEMA_OUTPUT_MISSING` at `extensions.bazaar.schema.properties.output`: the 402's Bazaar block had an input schema and no output schema.
Coinbase's own validator had said the same as advice (`bazaar.info.output`). The block now has what the reference package declares for an answer shown as an example.

- **`schema.properties.output`** is the reference package's own shape (`type`, and `example` as an object), so a validator that checks `info` against `schema` is
  satisfied. The package's validator (`validateDiscoveryExtension`) was run on the new block and says `valid: true`.
- **`info.output.example`** is the check's answer abridged to the keys that name what it returns: the subject, and for each listing the evidence level and the four flags
  with whether each is present (`true`, `false`, or `null` for not measured). A real answer also carries the dates, the sources, the basis of each flag and the
  statement. A test holds every key and value in the example to the API's own `CheckResponse` schema, so the example cannot name a field the API does not have.
- **Room for it.** The block grows from 790 to 1,185 bytes of JSON and the `PAYMENT-REQUIRED` line by 532 bytes, which would put the response header block at the edge
  over 4 KB. A payment reply (the 402 and its refusals, `sendReply` in `server/apiV1.ts`) therefore leaves out the five headers only a document needs: the
  Content-Security-Policy, the Permissions-Policy, the Cross-Origin-Opener-Policy, the Referrer-Policy and the X-Frame-Options, about 536 bytes. A program reads these
  replies; nosniff, HSTS and the cross-origin resource policy stay, and an answer and every other response keep all of them. The block at the edge was 3,930 bytes
  before. It measures 3,979 to 4,010 live after the change, not the 3,926 first projected, because Hostinger's CDN adds a Content-Security-Policy of its own
  (`upgrade-insecure-requests`, about 58 bytes) when the origin sends none; the other four headers are gone and the app's own policy is. That is about 90 bytes under 4,096, so nothing
  more should go into the 402 without making room again. The reference package's validator says `valid: true` for the block as served, and Coinbase's says valid with no advice left.
- **Service name and tags.** The Bazaar lists a service under a name and up to five tags (32 printable ASCII characters each), which the reference package reads from the
  `resource` of a settlement. 67 of 68 listings sampled carry them and ours had none.
  They are `Nooscape` and `agents`, `erc-8004`, `registry`, `pre-flight`, `due-diligence`, sent in the `resource` of the settlement to Coinbase only (`settleBody`),
  so the 402's header does not carry them, and Circle's body is what it was. **Not seen in the Bazaar yet:** the settlement of 22 October at 01:31 UTC carried them, and eight
  minutes later neither the stored entry nor the search row showed a name or tags, although the description, the extensions and the output had updated within a second. The
  reference package reads them from the settlement's `resource`, which is what is sent. So either Coinbase fills them in on a later pass, or it takes them from the 402's own
  `resource`, which would cost about 130 bytes of header that the block does not have (shorter tags would cost less). Open.
- **The refresh.** The operator paid once on Base on 22 October (01:31 UTC, transaction `0x61fedaf16fec7a78c72ea82a651b1a52fce25a84ed401425fc93d6d27fbe69ed`). The stored entry updated
  within a second and holds the output block. In the Bazaar's search, queries built from the description's own words rank it first or second; "check an AI agent in an ERC-8004 registry"
  ranks it tenth of 17, where it had been last of 16; the broad words (wallet, agent reputation, ERC-8004, trust check, Arc USDC) still do not return it. Coinbase counts 5 calls and one
  payer so far, all the operator's own: no outside buyer has been seen.
- **Not done:** an icon (`iconUrl`), ownership proofs, and the same output block for the lookup, which is not in the Bazaar or the root document.

## The standard form, and the listing at Tolly Labs (added 22 October 2026)

Tolly Labs runs an Arc directory of agents and services, the Agent Exchange (agent.tollylabs.com/agentic-market). Its form for a seller, read from the page's own script, has
four steps: describe the agent and the wallet it is paid to (signing in with a wallet, one message that moves no funds), prove the domain with a file at
`/.well-known/tolly-agent.json`, import the services from the seller's `/.well-known/x402`, and go live. The import calls each service without paying and checks that it asks for
USDC on Arc, to that wallet, at a fixed price of at most $10. The operator asked on 22 October to be listed there, as one more place where an agent can find the check.

Two things were missing. Their own well-known file is the standard form (`items`, each with `accepts`), and ours was x402scan's (`resources`, a list of addresses), which names no
method: a GET to the check, a POST route, answers 405, so an importer that tests a service with an unpaid call had nothing to go by. And there was no proof file.

- **The well-known file keeps its three fields and adds the standard form** (`x402WellKnown`): `x402Version: 2`, `pagination`, and `items` with one item, the check. The item has the
  resource, `type: "http"`, `accepts` (the terms of the 402, built by the same `requirements` function, so the two cannot differ), `lastUpdated` (the clock), the description, the MIME
  type, the service name and tags, and the Bazaar block, which says the method and a body to call it with. `accepts` lists Arc first, for a reader that takes the first entry and
  wants Arc; the 402 itself is unchanged (Base first). The receiving address is in `accepts[].payTo`, as in every 402, and nowhere else in the file.
- **`/.well-known/tolly-agent.json`** (`TOLLY_AGENT_PROOF`) is the file their form showed once the draft existed: `{ "agent": "nooscape", "operator": "0xe090fee7a47bcb744feac24ae92d134c04b3f8ab" }`.
  The agent is the id given in the form, for the domain `nooscape.si`; the operator is the wallet that signed in, in lower case, which is the receiving wallet. It is
  served as JSON, 200, no redirect, cached five minutes, and is the same whether payments are on or not: it proves a domain to a directory and says nothing about the payment. It is a
  route and not a file, like the other well-known files, because the static handler skips dot-directories.
- **What it does not do.** It registers nothing: the operator filled in the form and signs in with the wallet, and no key on this server could. It links no token: Nooscape has no
  token, Tolly is a venue for them, and the form's optional token step is left alone. It changes no term of the 402.
- **Checked.** `server/discovery.test.ts`: the standard item (its keys, the terms equal to the 402's, Arc first, Arc alone while Base is off, the Bazaar block, no secret, the address only as the
  payee of the terms) and the proof route (200, JSON, no redirect, the same with payments on, paused and not configured, HEAD, and the near-miss paths still reaching the page). Five deliberate
  breakages of the standard form and seven of the proof route were each caught.
- **Done.** PR 198 merged at 03:23 UTC (main 84d91bb) and the new document was live by 03:25. The operator then pressed "Check the domain" (domain proven) and "Import services"
  (1 service imported) on their page. Seen from outside afterwards, their public API lists the agent (`https://agent.tollylabs.com/v1/agents/nooscape`, and in `/v1/agents`) with
  the check as its one service, at $0.01, `resource` `https://nooscape.si/api/v1/check`, and our discovery document as its x402 endpoint. The page is
  `https://agent.tollylabs.com/agentic-market/#/agents/nooscape`. The import ran against the live 402 unchanged (Base first), so either their importer picks the Arc entry from the
  list or it took the terms from the document; the two are not told apart. Their own buyer client picks an offer by network and asset (`accepts.find`, read in their public MCP
  server), which points to the first.
- **Not done.** A token link (the form's token step is optional and Nooscape has no token) and a logo (the profile has none). Their page shows for each imported service when its
  last check passed and how many checks in a row failed (read from the script), so it is checked again from time to time: look there if the listing ever drops.

## What it will not do

- **It promises no listing.** An indexer decides for itself. x402scan reads the well-known file, but a third party's changelog says it indexes
  Base and Solana and not Arc (not checked here). The Coinbase Bazaar catalogs a route from a payment that settled through the Coinbase
  facilitator, and ours settle through Circle's Facilitator Service, which is also why the block cannot reach a catalog by being forwarded (Base, added later, is settled through Coinbase for that reason: see
  [x402-base-bazaar-2026-10-21.md](./x402-base-bazaar-2026-10-21.md)): the
  body we send the facilitator is built from our own terms and carries only the payment identifier as an extension. What the block does is
  describe the route to any client or validator that reads the 402. Circle's Agent Marketplace reads an OpenAPI document or a PDF, not this.
- **The lookup is not in the well-known file.** Within the free limit (30 a minute from one address) it answers 200, so an indexer that probes it
  would record a failure. It is in `/llms.txt`, and its 402 carries a block for the moment the limit is used.
- **No free text in the block, and (until 22 October) no output example.** The 402's `PAYMENT-REQUIRED` header is the base64 of the body, and a client
  sends the extensions back inside its payment, so each byte is carried three times. Measured on the built server, the 402's header block went from
  about 2.1 KB to 3.2 KB with the block (the header alone grew by 1,060 bytes, to 1.9 KB) and a standard client's payment header is 2.3 KB, against an 8 KB
  limit that an edge may apply to one line and a 4 KB buffer that some proxies use for the whole header block. The Bazaar refuses a listing whose metadata
  could be read as an instruction to an agent. The output example was left out for those bytes, and put in on 22 October because AgentCash's validator calls a
  block with no output schema an error, 67 of 68 listings sampled in the Bazaar carry one, and Coinbase ranks a listing by how complete it is: see "The output
  block" below. The OpenAPI document and `/llms.txt` say what the fields mean and what comes back in full.
- **It changes no term.** A payment is judged on the terms built in `requirements`, and `settleBody` builds what the facilitator receives
  from our own terms. A client that sends back a changed block is served exactly as before (checked, below).
- **No ownership proof.** The x402scan format can carry a signature by the receiving wallet over the origin. No key on this server can sign for
  that wallet, by design, so the field is left out.

## Shape, and how it was made

The two blocks were built with the reference package (`@x402/extensions` 2.28.0, `declareDiscoveryExtension` and the resource server's
`enrichDeclaration`) and the repo's output was compared with it: identical, with one intended difference. The check takes JSON only, so its
schema allows `bodyType: "json"` where the package lists all three. Both validate with the package's validator, and a version with a wrong
method, an agent with no id, a body with two of wallet and url, or no schema is rejected by it, so the pass means something.

The repo has no JSON Schema validator and none was added for this. `server/x402Bazaar.test.ts` pins both blocks exactly and checks the one
property that matters in code, that what `info` says is what `schema` allows. The block is 786 bytes for the check and 618 for the lookup.

## Checked live

On the day it merged, about 80 seconds after the deploy: `/llms.txt` answered 200 as plain text with the five-minute cache and the open headers, `/.well-known/x402` answered 200 with the check as its one resource, and the 402 of the check carried the 786-byte block. The reference validator accepted the block as served, the header and the body were the same document, and the price and the receiving address were unchanged. Seen from outside, the `PAYMENT-REQUIRED` header was 1,868 bytes and the whole response header block 3,406 bytes (the host's edge adds its own headers to the 3.2 KB measured on the built server), and the edge passed it. `verify-live` was 42 passed and 0 failed. Nothing was paid live: the one real payment on record is still the operator's earlier $0.01 test, so a payment that carries the block through the edge is checked on the built server and not on the host.

On 22 October, about two minutes after PR 198 merged (03:23 UTC, main 84d91bb; the new document was live at 03:25), 16 read-only checks passed against the live site: `/.well-known/tolly-agent.json` answered 200 as JSON with no redirect and the two fields; `/.well-known/x402` kept its x402scan fields and carried the standard form, one item with the terms for Arc then Base and the recipe for an unpaid call; the 402 of the check was unchanged (Base then Arc) with a response header block of 4,003 bytes, under 4,096; and `/llms.txt`, `/openapi.json` and `/.well-known/security.txt` still answered 200. The gate of the PR failed once, on `server/dbBreaker.integration.test.ts` (its control expects every one of 40 requests to fail with one error code against a real MySQL; it has flaked before) and passed on a re-run; nothing in the PR touches it.

## To look again

```bash
curl -s https://nooscape.si/llms.txt
curl -s https://nooscape.si/.well-known/x402
curl -s https://nooscape.si/openapi.json
curl -si https://nooscape.si/.well-known/tolly-agent.json
curl -si -X POST https://nooscape.si/api/v1/check -H 'content-type: application/json' -d '{"agent":{"chain":"arc","id":"1"}}'
```

The 402 must still carry `payment-required`, and the response header block should be about 3.2 KB. The operator's earlier $0.01 test payment is
the one that proves a client still pays through the edge. Public validators exist (`api.cdp.coinbase.com/platform/v2/x402/validate`, the
`@agentcash/discovery` command); each sends our address to a third party or runs downloaded code, so they are the operator's call.
