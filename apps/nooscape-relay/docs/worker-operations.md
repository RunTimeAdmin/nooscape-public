# Rate-limited ingestion worker operations

> **Current status (2026-10-13):** The production worker is enabled but bounded. It processes up to two due approved sources per tick (raised from one by migration 0027) and supports seven scheduled protocols: `a2a`, `catalog`, `census`, the `erc8004` activity walk (scheduled by 0017), the Metaplex `solana_registry` chain pass (scheduled by 0021, 15-minute cadence), the `solana_8004` chain pass (scheduled by 0027, 30-minute cadence), and the `solana_said` identity pass (scheduled by 0031, 60-minute cadence). `erc8004_reputation` and `usdg_settlement` remain manual-only and are rejected by the worker.

## Production model

Nooscape uses a host-managed scheduled invocation of the authenticated worker-tick procedure. The worker is controlled by a database singleton rather than in-memory state, so it remains safe across application restarts and cannot create an arbitrary fetch target.

## Enforced production limits

| Control | Value |
|---|---:|
| Host schedule | Every 15 minutes |
| Database global minimum interval | 15 minutes, less 30 seconds for a tick that arrives early (`CLAIM_EARLY_TOLERANCE_MS`) |
| Maximum sources per tick | 2 (migration 0027; was 1) |
| Source cadence | `scheduleMinutes` per approved source (daily for metadata sources; 15–30 minutes for the chain passes) |
| Scheduled protocols | `a2a`, `catalog`, `census`, `solana_registry` (Metaplex chain pass, 0021), `erc8004` (activity walk, 0017), `solana_8004` (chain pass, 0027), `solana_said` (identity pass, 0031) |
| Manual-only protocols | `erc8004_reputation`, `usdg_settlement` — rejected by the worker |
| Request behavior | Approved source boundary only; bounded, metadata-only adapter behavior; no credentials, cookies, tool invocation, or payment flow |

A source's next run is set when its run finishes (`finishIngestionRun`: finish time plus `scheduleMinutes`) and the cron fires on fixed 15-minute marks, so a source whose cadence is a multiple of 15 minutes becomes due just after a tick and waits for the next one. Treat `scheduleMinutes` as a floor: the identity registry, set to 15 minutes, was observed succeeding at 18:30:03Z and 19:00:25Z on 2026-10-13. The 3-hour freshness limit in `scripts/verify-live.mjs` absorbs this.

**The worker is at capacity.** Due sources are taken oldest-due first, two per tick, four ticks an hour: eight runs an hour. Three sources set to 15 minutes (the Robinhood identity registry, the Metaplex registry, BNB Chain) each really run every 30 minutes, 8004 about every 45, SAID about every 75, and the daily sources add a few more, so the demand is about eight runs an hour as well. Adding a source or lengthening a run therefore stretches every cadence a little. Observed 2026-10-14: the BNB Chain source, nominally every 15 minutes, got a slot every 30 to 45 minutes (05:45, 06:30), so its backfill takes 15 to 25 hours, not the 17 first estimated. Raising the slots per tick (the control plane allows one or two, migration 0027) would be the lever, and is a decision.

**Lost ticks, and the early-tick tolerance (2026-10-20).** The claim refused a tick that came less than 15 minutes after the last claim, and the cron's request reaches the app a few seconds either side of :05, so a tick that arrived a second before the previous tick's offset was refused and nothing ran: 3 of the 11 ticks from 21:00 to 23:30 UTC (the 23:30 tick was refused, the last claim being 23:15:05). `CLAIM_EARLY_TOLERANCE_MS` (30 seconds, `server/db.ts`) now lets such a tick in; a manual tick or a second instance still waits 14.5 minutes. With eleven scheduled sources the two slots are still the limit. A simulation of the queue as read from the database at 23:37 gave the Base source 23 runs a day before the change and 41 after, and BNB Chain 20 before and 34 after, against a nominal 48. The record is [Base backfill throughput](./base-backfill-throughput-2026-10-20.md).

The worker checks the database control plane first. When paused, it makes no external request. When enabled, it selects only active sources whose `nextRunAt` is due, runs up to the configured per-tick maximum (currently two), and records the result in the normal append-only run/evidence model.

## Source-specific rules

- **A2A:** exactly one approved AgentCard metadata resource per source run.
- **Catalog:** one bounded approved snapshot with parser, record, and response limits; do not dereference advertised agent/provider URLs.
- **Census:** one bounded aggregate document; never create an agent identity/profile.
- **Solana registry (Metaplex chain pass, 0021):** scheduled at a 15-minute cadence — chain-facts-only state-diff reads through the shared paced RPC client, INSERT-IGNORE ledger writes, and a snapshot persisted only after every attribution succeeds; a failure leaves the cursor untouched.
- **Robinhood ERC-8004 activity walk (0017):** scheduled at a 15-minute cadence — the forward, reorg-checked walk adds no reviewed records; a reorg fails the run loudly with the cursor untouched.
- **SAID identity pass (0031):** scheduled at a 60-minute cadence after an operator seeded it. Directory-only: one memcmp-filtered `getProgramAccounts`, strict fail-closed decode, a 98%-of-prior enumeration floor, and an upsert that adds no reviewed record. A failure leaves the cursor and the directory untouched. SAID identities are never closed on chain, so a missing identity is counted in the run result and never hidden. See [said-solana-2026-10-13.md](./said-solana-2026-10-13.md) section 9.
- **AgenC registry pass (`solana_agenc`, migration 0051 by hand):** staged manual-only and not yet run. The worker cannot claim it until a reviewed flip (0053, a daily cadence; 0052 went to the Ethereum flip) hands it to the scheduler, after an operator has run it and compared the count to the chain. Directory-only like the SAID pass: one memcmp-filtered `getProgramAccounts`, a strict fail-closed decode of the fixed 566-byte AgentRegistration, a 98%-of-prior enumeration floor, and an upsert that adds no reviewed record. AgenC never closes an agent (deregistering leaves an Inactive tombstone), so a missing agent is counted in the run result and never hidden. See [the record](./agenc-solana-2026-10-26.md).
- **BNB Chain identity pass (`erc8004_bsc`, 0035):** scheduled at a 15-minute cadence (about one run every 30 minutes, see above) after an operator ran the first pass; the flip's WHERE requires the approved source key and protocol, an active manual-only source with a `bsc:` cursor, a recorded success, and no failure. Directory-only chain facts from finalized blocks through the keyed `BSC_RPC_URL` endpoint, in windows of at most 50,000 blocks applied in chain order under a `bsc:` cursor; it never fetches a URI. A run is bounded (60 windows, 30 s, 20,000 events), keeps the progress it made if a later window fails, and fails loudly if it cannot make any. Registrations go to their own table, not the directory; after the windows a listing refresh classifies them against the published rules and, once the walk reaches the finalized head, publishes the passing ones (a few thousand of the 373k) into the directory; a refresh failure is logged and never fails the run. See [bsc-erc8004-2026-10-13.md](./bsc-erc8004-2026-10-13.md).
- **Arc identity pass (`erc8004_arc`, 0050):** scheduled once a day (1440 minutes) after an operator ran the first passes; the flip's WHERE requires the approved source key, an active manual-only source with an `arc:` cursor, a recorded success, and no failure (it does not name the protocol, because no SQL run at boot may name the by-hand migration 0046's values). It is the BNB Chain pass on another chain: chain facts from finalized blocks through the Arc node (`X402_RPC`), windows of at most 100,000 blocks applied in chain order, a run bounded to 10 windows, 20 seconds and 1,000 events, and it never fetches a URI. Arc finalizes instantly, so a run that reaches the head publishes the listing in the same run. A day of Arc is about two windows, so one run a day has room; if Arc ever registers more than 1,000 agents a day the cadence has to shorten. A failed run is tried again a day later (`finishIngestionRun` adds the cadence whatever the outcome), and until then the source shows a failure and the live check fails. The pass does not start while the `chain_arc` switch is off, and a scheduled run then records a failure. The live check expects a success within 36 hours.
- **Ethereum identity pass (`erc8004_eth`, 0052):** scheduled once a day (1440 minutes) after an operator ran the first pass; the flip's WHERE is the Arc flip's with the Ethereum source key and an `eth:` cursor, and it names no protocol. It is the BNB Chain pass on another chain: chain facts from finalized blocks through the keyed `ETH_RPC_URL` endpoint, windows of at most 2,000 blocks applied in chain order, a run bounded to 100 windows, 30 seconds and 5,000 events, and it never fetches a URI. A day of Ethereum is about 7,200 blocks, four windows, and the registry gains about 130 registrations a day, so one run a day has room; if Ethereum ever records more than 5,000 events a day the cadence has to shorten. A failed run is tried again a day later, and until then the source shows a failure and the live check fails. The pass does not start while the `chain_ethereum` switch is off, and a scheduled run then records a failure. The live check expects a success within 36 hours. See [the record](./ethereum-go-live-2026-10-27.md), section 9.
- **8004-solana chain pass (0027):** scheduled at a 30-minute cadence — chain-facts-only diff with INSERT-IGNORE ledger writes, a 98%-of-prior-live enumeration floor, and per-closure confirmation reads.
- **BNB fleet and template clustering (0038):** a best-effort step after the sources and the Owl's Catch, only on a tick that claimed sources. It reads `tokenURI` for the listed entries without evidence through Multicall3 at 75 CU/s (at most 40 batches and 20 seconds a run), recomputes the registry's fleets every 6 hours and stores gate G1 on each listed entry. With the tables missing (migration 0038 not run) it does nothing and logs nothing; any other failure is one `nooscape_bsc_clusters_failed` line and never fails the tick. It also stores the endpoint-host groups (hosts that 50 or more listed entries declare as their agent address host) in `bsc_endpoint_host_groups` (migration 0040); with that table missing it skips that part alone. Nothing reads the table. See [bsc-clusters-2026-10-16](bsc-clusters-2026-10-16.md).
- **Robinhood names:** a best-effort step after the BNB steps, only on a tick that claimed sources. It reads the registration link that a reviewed Robinhood record's summary names, when the record's name is still "Agent #n", through the shared safe fetch (robots.txt first, a second between requests to a host, the configured IPFS gateway for ipfs links), at most 16 files a run and 6 from one host, nothing started after 20 seconds, only on a tick under 100 seconds old, a run at most every 30 minutes (the gate between two runs is 28 of them, `server/stepInterval.ts`: a step starts at a different time in each tick, and a gate of exactly 30 skipped every other tick once the rater fill ended), a link tried again no sooner than 6 hours after its last try and never past the Solana reader's tries. It also names the acknowledged Robinhood directory entries: for the entries that show "Agent #n" and have no recorded link it reads `tokenURI` from the chain in one Multicall3 `eth_call` of up to 16 reads (one attempt; a 403 or 429 pauses chain reads for 2 hours, any other failure for 30 minutes), records the hash of each link on the entry, queues the https and ipfs ones and writes a name that was read to the entries it belongs to, with a sentence in the entry's note. It keeps the answers in `agent_registration_resolutions` (no migration); a reviewed record's name is laid over the placeholder when the record is served. It never throws and a failure is one `nooscape_robinhood_names_failed` line. See [approvals/2026-10-17-robinhood-names](approvals/2026-10-17-robinhood-names.md) and [approvals/2026-10-17-robinhood-entry-names](approvals/2026-10-17-robinhood-entry-names.md).
- **BNB registration files:** a best-effort step after the Robinhood names, only on a tick that claimed sources and is under 100 seconds old. It reads the file behind the https or ipfs link of a listed BNB entry whose evidence says `link_not_read`: the entry's `tokenURI` again in one Multicall3 `eth_call` (through the clustering step's compute-unit bucket; chain reads pause for 30 minutes after a failure), then the file through the shared safe fetch (256 KiB, robots.txt first, a second between requests to a host, the configured IPFS gateway for ipfs links), at most 16 files a run and 6 from one host, nothing started after 20 seconds, a run at most every 30 minutes (28 for the gate, as for the Robinhood names), a link tried again no sooner than 6 hours after its last try and never past five tries (a link that does not answer) or two (a file that is not a registration). It keeps the entry's template key and first agent-address host and works G1 and the groups out again. It asks no agent address. It never throws and a failure is one `nooscape_bsc_files_failed` line; with the clustering tables missing it does nothing. See [approvals/2026-10-17-bnb-registration-files](approvals/2026-10-17-bnb-registration-files.md).
- **Base and Arc names:** a best-effort step after the SAID names, only on a tick that claimed sources and is under 100 seconds old. It takes one chain a run, Base and Arc in turn (a chain that is switched off, has no active source or has nothing to ask leaves the run to the other). For a chain it first lays names that were read over entries that show "Agent #n" again (no request), then reads `tokenURI` for up to 16 entries that show the placeholder and have no row in `agent_registration_resolutions`, newest first, in one Multicall3 `eth_call` on the chain's own node at the finalized block (one attempt; a 403, a 429 or a busy answer pauses that chain's reads for 2 hours, any other failure for 30 minutes). A link counts only when its hash is the one the registry row recorded. It queues the https and ipfs links, names an entry at once from JSON inside its link, and records everything else as settled so it is not read from the chain again. It then reads the queued links through the shared safe fetch (robots.txt first, a second between requests to a host, the configured IPFS gateway for ipfs links) at the Robinhood pace: at most 16 files a run and 6 from one host, nothing started after 20 seconds, a run at most every 30 minutes (28 for the gate), a link tried again no sooner than 6 hours after its last try and never past five tries (a link that does not answer) or two (a file with no name). A name that was read is written to the entry only where the name is still the placeholder, with a sentence in its note. It keeps the answers in `agent_registration_resolutions` (no migration), never throws, and a failure is one `nooscape_chain_names_failed` line. To stop it, pause the chain's source. See [approvals/2026-10-26-base-arc-names](approvals/2026-10-26-base-arc-names.md).
- **BNB rater credibility (0039):** a best-effort step after the clustering, only on a tick that claimed sources. It reads the BNB Chain reputation registry's NewFeedback and FeedbackRevoked events window by window at 75 CU/s (one bucket shared with the clustering), pins the registry's implementation and stops if it changes or a log does not decode, and, once caught up, stores each rated agent's independent raters in `bsc_rater_evidence`. Internal only. With the tables missing (migration 0039 not run) it does nothing and logs nothing; any other failure is one `nooscape_bsc_raters_failed` line and never fails the tick. See [bsc-rater-credibility-2026-10-16](bsc-rater-credibility-2026-10-16.md).
- **Manual-only protocols:** `erc8004_reputation` stays operator-paced until it earns the same reviewed policy flip the activity walk received (design §7), and `usdg_settlement` remains a bounded manual run; both are rejected loudly by the scheduled worker. A manual run requires its own source review, evidence review, and projection decision.

## Hostinger cron boundary

The production cron invocation calls the operator-protected `liveData.admin.runWorkerTick` procedure. Its authentication value is managed in Hostinger, never committed to source control, emitted in application responses, or exposed to the browser.

The job is a POST every 15 minutes (`*/15 * * * *`) that sends the operator header (`x-nooscape-operator-token`) and the body `{}` to `/api/trpc/liveData.admin.runWorkerTick`, with `curl -fsS --max-time 150`. What to know when it misbehaves:

- **The body must contain no double quotes.** Hostinger's cron runner strips them from the command (seen 2026-10-14: `{"json":null}` arrived as `{json:null}` and every tick got HTTP 400). `{}` parses and needs none. A Windows shell does the same: write `{"json":null}` to a file and send it with `--data-binary "@body.json"`, or run the call from the host's Linux terminal.
- **A tick takes up to about 100 seconds** (the agenstry catalog snapshot is the long one). The CDN answers 504 after about a minute, so the job's output usually reads `curl: (22) ... error: 504` even when the tick ran. The server finishes the tick regardless; check `liveData.sourceStatuses`, not the exit code.
- **The 15-minute global interval runs from the last claimed tick.** A manual tick makes the next cron tick answer `"state":"rate_limited"` with nothing run, which looks like a failure and is not.
- **To tell whether the schedule is running,** read `updatedAt` on the scheduled sources in `liveData.sourceStatuses` (it advances every 15 to 30 minutes), and the job's last output with `hosting_cron-jobs_output` or in hPanel. After any plan or account change, check both within the hour.

### The second job: the agent checks

A second cron job calls `liveData.admin.runChecks` (same header, same `{}` body, the schedule and the command are in [agent-checks-2026-10-16](agent-checks-2026-10-16.md)). It is separate because the ingestion tick is at capacity. What to know when it misbehaves:

- **It answers with counts, normally in well under a minute.** A run starts no address after 20 seconds, so unlike the tick it normally ends before the CDN's minute (a write can wait up to 30 seconds for a connection) and `curl` prints the JSON (`state`, `due`, `asked`, `answered`, `noAnswer`, `skipped`, `notReached`, `recorded`).
- **`"heldBack"` above zero with `"taken":0` means writes are failing,** not that nothing is due: the process holds back addresses it asked within the day whose rows were lost, and says so in the answer and the log.
- **`"state":"unavailable"` means nothing was asked.** The checks table cannot be read: migration 0037 has not been run, or the database is busy. The runtime log carries one `nooscape_checks_failed` line with the reason. **`"state":"busy"`** means another run is going in the same process.
- **A 401 means the token in the job's command is not the app's.** `runChecks` uses the same check as the worker tick, so copy the `x-nooscape-operator-token` value from the working tick job. Nothing is logged for a 401, and failed header attempts are not counted toward any lockout (only the login form counts failures).
- **`"state":"completed"` with `"due":0` is normal when nothing is eligible.** Today two live cards declare an address (a top-level `url`, or a `supportedInterfaces` entry), and an endpoint whose card changed after the operator approved a run waits for the next approval. A run that asks nothing writes no log line.
- **Its database cost is small.** A handful of reads and up to 40 inserts a run, over the connections the pool already holds. It opens none of its own, so it does not spend the hourly connection budget.
- **It does not run the ingestion tick** and does not touch its interval: a manual `runChecks` never makes the next tick answer `rate_limited`.
- **To stop it,** delete the cron job. Nothing else needs undoing.

### The third job: webhook deliveries

A third cron job calls `liveData.admin.runWebhooks` (same header, same `{}` body; the record is in [data-access-2026-10-19](data-access-2026-10-19.md), stage D5). It is separate because the ingestion tick is at capacity. The schedule is `*/5 * * * *` and the command is the tick's with the last word changed:

```text
curl -fsS --max-time 90 -X POST -H 'x-nooscape-operator-token: <the operator token>' -H 'content-type: application/json' -d '{}' https://nooscape.si/api/trpc/liveData.admin.runWebhooks
```

- **It answers with counts, normally in seconds.** It sends for at most 45 seconds, so a 504 from the CDN would be new information, unlike the tick's, which routinely shows one while it runs. A healthy answer is `"status":"ran"` with `created`, `sent`, `retrying`, `gaveUp`, `disabled`, `purged`, `failed` and `fullReads`. Every count is 0 while no key has a webhook and a watch.
- **`"status":"off"` has a `reason`.** `WEBHOOK_SIGNING_KEY is not set` (or too short) means the setting did not take or the app was not restarted; `the webhook tables do not exist yet (migration 0045)` means the paste did not reach the production database. **`"busy"`** means another run was still going. **`"error"`** means the database could not be read, and the cause is only in the runtime log.
- **`failed` is not 0** when a database error stopped one webhook's deliveries for the run: the other webhooks and the tidy step went on, the cause is in the runtime log ("[Webhooks] deliveries for one webhook failed"), and the deliveries are tried again by a later run.
- **`fullReads` is not empty** when a read stopped at its limit: that run did not move its cursor, and the next one reads again, so nothing is skipped.
- **A 401 means the token in the job's command is not the app's.** Copy the `x-nooscape-operator-token` value from the working tick job, and never paste it into a document.
- **It writes only its own tables** (`api_watches`, `api_webhooks`, `api_deliveries`, `api_event_cursors`), sends only to https addresses that a Builder or Pro key set, through the guarded fetch, and tidies deliveries older than 30 days at most every six hours.
- **To stop it,** delete the cron job. Events then wait, and are sent when it runs again. To switch webhooks off altogether, unset `WEBHOOK_SIGNING_KEY` and restart.

## Build host

Pushing `main` makes Hostinger clone the repository, run `pnpm install` against its own package store, and run `pnpm run build`. If the build fails, the site is not redeployed, and pressing Redeploy repeats the same failure.

**2026-10-14 esbuild `EACCES`.** From about 11:50Z every build failed in `vite build` with `spawn .../node_modules/.pnpm/@esbuild+linux-x64@0.28.2/node_modules/@esbuild/linux-x64/bin/esbuild EACCES`, for a commit that had built at 11:19Z. The binary had lost its execute bit. pnpm hard-links packages out of one store, so a bit lost there comes back with every install, and rebuilding `node_modules` does not help. Nothing in the repository had changed. pnpm 10 skips esbuild's install script (`Ignored build scripts: esbuild`), and enabling it does not help: the script runs the binary and fails if it cannot, so it would turn a build failure into an install failure. What caused the bit to be lost on the host was never established.

`pnpm run build` now starts with `scripts/ensure-esbuild-executable.mjs`, which adds the execute bit to any esbuild platform binary under `node_modules/.pnpm` that lacks it (and to the directories on the way) before `vite build` runs. It changes nothing when the binaries are already executable, prints a line when it repairs one (`[build] restored the execute permission on 1 esbuild path`), and never fails the build itself. It was checked on Linux as a non-root user against the exact failure, including a reinstall from a store whose copy had lost the bit (`server/esbuildPermissions.test.ts` covers it, and CI runs that on Linux). If a build log still shows `EACCES` after that line, the host's permissions are worse than a missing bit (a read-only or `noexec` filesystem, or a file the build user does not own): look at `ls -l` of the path in the error from the host's terminal.

**Node version.** The host's log prints `Node.js: 22` and nothing about the patch release. `pnpm run build` ends with `node -v`, so the exact version the build ran on is the last line of the build output. Read it there after a Node security release (the October 2026 fix for the 22 line was 22.23.4). Nothing in the running app reports its own Node version.

## Database connection budget

The host caps the database account at 500 new connections an hour (`max_connections_per_hour`). Past the cap it refuses every new connection until the hour turns over, and the runtime log carries `ER_USER_LIMIT_REACHED`. Calls that land on an already-open pooled connection keep working, so the site degrades unevenly:

- The operator console shows "Live data is temporarily unavailable." and raw `Failed query: select ... from users ...` errors (operator sign-in reads that table).
- `liveData.availability` answers `persistentStorageConfigured: false`, and `verify-live.mjs` fails its storage check.
- Cached public reads, and queries that happen to hold an open connection, still answer.

This happened on 2026-10-14 at 03:03Z and cleared on its own within the hour. The cause was connection churn, not traffic. The pool retired idle connections on a timer (`maxIdle` 5, `idleTimeout` 45 s), and mysql2 destroys every free connection beyond `maxIdle` within a second, so a page load or console refresh after a quiet moment reopened up to ten connections. Pages that poll every 8 to 20 seconds spent the budget. The pool now keeps its connections (eight for everything and two for searches, ten per process as before): `DB_POOL_OPTIONS` in `server/db.ts` sets `maxIdle` equal to `connectionLimit`, which leaves mysql2's idle reaper off, and TCP keepalive probes every 10 s so an idle connection is not dropped without notice. `dbPool.integration.test.ts` fails if a second burst after a quiet moment opens any new connection.

- **Do not deploy or restart during a lockout.** The boot-time migration runner needs a fresh connection and the app refuses to serve if it cannot get one, so a restart inside the lockout can take the whole site down. Wait for the counter to turn over, confirm `verify-live.mjs` passes, then deploy.
- **Read the cause in the runtime log, not the console.** The console shows only the wrapped driver message; the `[LiveData] storage failure:` line names the MySQL error.
- **The pool warns before the cap.** A process opens about ten connections and keeps them. The runtime log line `[Database] 150 connections opened within an hour` means something is churning again (a host that drops idle connections, or a code path that bypasses the pool). Treat it as a fault to fix, not as noise, since the host refuses new connections at 500.
- A deploy opens a new pool (Hostinger boots the app twice), so it costs about ten connections each time. That is small against the budget, but it is not free.
- **A refusal pauses new connection attempts.** `server/dbBreaker.ts`: when the host refuses a new connection (`ER_USER_LIMIT_REACHED`, `ER_TOO_MANY_USER_CONNECTIONS`, `ER_CON_COUNT_ERROR`, `ER_HOST_IS_BLOCKED`, or the network failures of a connect), the app stops dialling it for 10 seconds, then lets one attempt through. A refusal doubles the wait (20 s, 40 s, up to 120 s); an accepted connection ends the pause. Connections the pool already holds keep working. While it is paused, a request that needs a new connection fails at once with `DB_CIRCUIT_OPEN`, as it does under a refusal, and the runtime log carries two lines per episode (`[Database] The host refused a new connection` and `[Database] The host is accepting connections again; N attempts were held back`) instead of one per failed request. Replaying the hourly cap in the pressure test, the host saw 590 connection attempts in 30 seconds before this; with it, it refused 2 in the minute.
- **A request waits a bounded time for a connection.** `guardPool` in `server/dbBreaker.ts` answers a request that has waited more than `DB_ACQUIRE_TIMEOUT_MS` (30 seconds) for one of the eight connections with `POOL_ACQUIRE_TIMEOUT`, which the public reads treat like any other database failure and answer with their empty result. Without it, a database that stopped answering held every connection in a hung query and every request behind them waited as long as the freeze lasted (the pressure test's 20-second freeze: poll p95 26 s). The limit is long on purpose: while the cached aggregates rebuild they hold most connections for several seconds, and a visitor who waits that out gets a right answer where a short limit would give an empty one. A search is declined as `busy` after 10 seconds (`SEARCH_ACQUIRE_TIMEOUT_MS`). The main pool's `queueLimit` of 2,000 is only a memory valve. Not applied: a server-side statement time limit on the shared pool, because the aggregate rebuilds and the worker's statements legitimately run for seconds and there is no production timing for them yet (the search pool keeps its 8 seconds).

## Public read cost

Measured with the local pressure-test harness (`scripts/loadtest`): the production build against a database seeded to production scale (about 247k directory entries, 373k BNB Chain registry rows, 82 reviewed records). The numbers come from a 4-core PC shared by MySQL, the server, and the load generator, so read them as relative.

- **A visitor is cheap.** With the aggregates cached, a Home poll (seven reads every 20 s) takes about 20 ms of server time, an entry page 15 to 30 ms, an agent page about 50 ms.
- **The aggregates are not.** Rebuilding the cached directory counts takes MySQL to 500 to 700% CPU for 4 to 8 seconds, and every other query waits behind it. The cost is the same whether 1 or 500 people are watching, so what matters is how often it happens.
- **The chain tabs add one read, polled every 60 seconds.** `liveData.chainStats` (`readChainStats` in `server/db.ts`, the mapping in `shared/chains.ts`) puts each protocol on its chain (`erc8004` and the reputation and USDG ledgers on Robinhood, the three `solana_*` protocols on Solana, `erc8004_bsc` on BNB) and builds the figures only from reads that already apply the public rules: the directory breakdown (cached, visible entries only), the reviewed records (read live, never cached, so a withdrawal shows at once; about 10 ms) and the ratings count (cached and dropped by an operator's write, joined to visible Robinhood identities, so a hidden or closed entry's ratings never count). A chain with no active source is reported as not indexed, not as zero, and Solana and BNB have no ratings figure yet (not measured).
- **Text search was the outlier.** Every text query cost 2 to 5 seconds of database time, whatever it matched, while a wallet-prefix search took 40 ms, and the Home page sent one per keystroke. It now runs a query per index and merges them, counts up to the cap for real, runs on a pool of its own, and is held for a minute (see below); a first call is 0.3 to 0.5 s for a common word and tens of milliseconds for a rare one.

What the cache does about the first two (`server/readCache.ts`, `server/warmReads.ts`):

- **A 5-minute TTL, not 30 seconds.** Every write that can change a count drops the cached aggregates or marks them stale (see "Two kinds of invalidation"), so the TTL only bounds changes made behind the process's back. `NOOSCAPE_DIRECTORY_CACHE_TTL_MS` still tunes it, and `0` turns caching off.
- **Refresh-ahead.** Once a value is within 30 seconds of expiry, the next read reloads it in the background and keeps serving the current value, which is never older than the TTL. A failed reload is never stored and is retried no sooner than 5 seconds later; at expiry the next read loads in the foreground and fails closed, as before.
- **Warm-up.** The aggregates are built when the server starts (Hostinger boots the app twice on every deploy) and again 4 seconds after a burst of writes settles, but only if someone has read them in the last 5 minutes. After an ingestion write its own reads are what start the background reload, when no visitor's read has.
- **Changes made behind the process's back show up within the TTL.** A manual edit in the database console does not invalidate anything, so counts can lag it by up to 5 minutes (restart the app to refresh at once). A migration applied at boot is unaffected: the cache starts empty after it.
- **Two kinds of invalidation.** An operator's write (a hide or unhide, approving, pausing or rejecting a source) drops the aggregates and the held searches, so the very next read comes from the database and shows it. An ingestion write (directory upserts and closure markers, both activity ledgers, the BNB registry rows and listing) only marks the aggregates stale. Visitors keep getting the current counts at once, and one background reload replaces them after the writes have been quiet for 3.5 seconds, so a run of window writes costs one rebuild and nobody waits for it. The new counts show about 10 seconds after the last write at 240k rows (the 4-second warm-up delay plus the rebuild), or by the time the TTL runs out during a long unbroken run. A reload that fails leaves the old value in service and is retried no sooner than 5 seconds later, and one that a later write overtakes is followed by another after the next quiet period. `server/directoryInvalidationKinds.test.ts` pins every write to its kind. Before this, the visitors arriving in the seconds after any write waited for the rebuild.
- **Searches have a pool of their own.** `SEARCH_POOL_OPTIONS` in `server/db.ts`: two connections and a queue of ten, taken from the ten each process already held (the main pool is eight). One search holds one connection for all its queries. Past ten waiting, a search is declined with `busy: true` (the Home page says so) and logged at most once every 10 seconds, instead of queueing the page polls behind it. MySQL stops a search that runs past 8 seconds. Results are held for a minute. An operator's write drops them, so a hide or a pause leaves the results on the very next search; an ingestion write does not, so a new entry can take up to a minute to be found.
- **Evidence is read live.** The homepage polls one agent's evidence every 8 seconds per visitor, and a reviewed record's evidence is never held, because its visibility and publisher status are read live. (Until 2026-10-17 an illustrative demo agent's evidence was held for 5 seconds; the demo atlas is deleted.)

Effect on 500 simulated viewers for 75 seconds, one machine, the same scenario before and after: evidence median 3 to 7 s down to 3 ms, first page load median 2 to 10 s down to 0.2 s, poll median 1.2 to 4 s down to 0.65 s, all 83 requests a second served with no errors and no new database connections after warm-up.

Rerun it with `pnpm exec tsx scripts/loadtest/seed.ts` (builds the database) and `node scripts/loadtest/run.mjs --spawn --database nooscape_load --viewers 500 --duration 75`. See the README in that folder.

## Operational controls

- **Pause immediately:** set worker state to `paused` through the operator route; subsequent cron invocations return `paused` without a fetch.
- **Rate-limit adjustment:** change only the database configuration; minimum global interval is 15 minutes and maximum sources per tick is one or two (currently two, migration 0027).
- **`tickSeconds` is gone from the code.** The worker configuration once carried a tick length that was stored and validated and that nothing read: the tick is bounded by the cron's 150 seconds and by what each source does (a scheduled Robinhood call waits out a throttle for 5 seconds, `SCHEDULED_RPC_RETRY_BACKOFF_MS`). The operator route `configureWorker` no longer takes it and the schema no longer names it; the column stays in the table, with its default of 900, until the operator drops it. That is migration 0049 (`drizzle/0049_drop_worker_tick_seconds.sql`, one `ALTER TABLE ... DROP COLUMN`), which the boot runner never applies: paste it into the SQL console when it suits, then read `nooscape_schema_migrations` and record the version under the next free number if 49 is taken. The code runs the same before and after.
- **A refusal is not an outage.** When a rule of the product refuses an operator's request (the four-eyes rule on a publisher key, a domain the agent has not asserted, a challenge that is no longer pending, a key or an identity that is not there), the console says the rule in its own words (`OperatorRuleError`, `server/operatorRuleError.ts`). "Live data is temporarily unavailable." now means a fault of the database, and only that; its cause is in the runtime log.
- **Source pause/revocation:** source-level state remains authoritative and takes effect before a scheduled request.
- **Failure handling:** a source failure is recorded and source cadence advances. The tick keeps going with the other claimed source (each run owns its own run row, cursor, and error), and the tick result reports every failure.
- **Review before projection:** inspect the complete latest completed run’s retained evidence before a new source projection decision. A successful scheduled run never means automatic public trust promotion.

A standalone `pnpm worker:tick` entrypoint exists for a future dedicated worker host. It obeys the same database control plane and starts in a non-fetching paused state.
