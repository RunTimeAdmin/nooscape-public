# REST API: what the directory holds on each chain (2026-10-26)

Status: **LIVE (merged 2026-10-26 at 22:14 US Central, answering from 22:15), and the matching `get_stats` tool is published as `nooscape-mcp` 0.3.0.** Stage 2 of the operator's "1 then 2 then 5" (stage 1 was the Base and Arc names, [the record](./approvals/2026-10-26-base-arc-names.md)). It needed no migration, no setting and no approval to run. Section 7 records the launch.

## 1. What this adds

`GET /api/v1/stats`: one JSON answer with a row for each chain the API serves, holding the counts the chain tabs on the home page show. Until now a caller could look an agent up or search, and had to read the site to learn how many entries Nooscape lists on a chain. The competitor scan of 2026-10-26 found that the other ERC-8004 explorers give these counts as an answer of their own.

It writes nothing and adds no table, migration, setting, source or request to a chain or a third party. It reads the same rows the home page reads.

## 2. The answer

The envelope is the one every answer has: `api_version`, `as_of`, `source` (`kind: directory_stats` and the chains), `license`, `data`. `data` holds `statement`, `totals.acknowledged` (the listed entries on the chains below, added up) and `chains`.

| Field of a chain | Where it comes from | `null` means |
|---|---|---|
| `chain`, `label`, `chain_id` | the API's own chain table | `chain_id` is null on Solana |
| `indexed` | the site's chain figures: at least one active source reads the chain | (never null) |
| `acknowledged` | the entries listed under the public rules: not hidden, not closed, from an active source, on a chain whose switch is on | the chain is not indexed |
| `ratings_recorded` | the reputation ledger (Robinhood Chain), the 8004 registry's own counters (Solana), the ratings step (Base, Arc, Ethereum) | not counted, which is not zero |
| `registrations_on_chain` | the registry rows the chain pass stored (BNB Chain, Base, Arc, Ethereum) | not counted there, or the count is not complete yet |
| `new_in_24h` | entries by their own first-seen time | the chain is not indexed, or the count could not be read |
| `registries` | how many entries each registry lists, largest first, with its contract (null on Solana) | (an empty list while not indexed) |
| `last_read_at` | the newest success of an active source of the chain | no source has read it |

The rows follow the chains the API serves: Robinhood Chain, BNB Chain and Solana, then Ethereum, Base and Arc as their switches go on. With every switch off, nothing of those three is in the answer or in the document.

## 3. Choices

- **One endpoint.** The scan proposed `/stats` and `/chains`. One answer with a row for each chain carries both, and `/api/v1` already lists the chains.
- **The site's own reads.** The route calls the three public procedures the home page calls (`liveData.chainStats`, `arrivals` and `directoryBscRegistry`) through `appRouter.createCaller`, as the claim answers do. The API cannot count differently from the site, and a hidden entry or a paused source leaves the answer when it leaves the site's.
- **No cache of its own.** Those reads keep their counts for up to five minutes. A second cache on top would have made the answer older than `as_of` says, so `as_of` is when the answer was built and the document says the counts behind it are kept for up to five minutes. A caller's browser may hold it for a minute (`private, max-age=60`, as a search is).
- **A failed read fails.** If the site's chain read gives no chains, it did not read. The endpoint then answers 503 with `Retry-After: 30` and the cause kept out of the body, and never a directory with nothing in it. A missing arrivals count or BNB registry count leaves that one figure null and does not fail the answer.
- **`reviewed` is left out.** The tabs also show how many reviewed records list a chain. The REST API serves acknowledged entries only and gives no tier, so it says nothing of reviewed records here either.
- **No option.** A query string is refused with 400 before any read, so it cannot be used to ask for the read again.
- **No key.** It is open at the public limit (30 a minute). A call with a key counts as one request, is named `stats` in the usage report, and gets the same answer on every tier.
- **Words.** `data.statement` says what the counts are and are not: a count of listed entries is not a count of the agents that exist or work, and a registration that the published listing rules do not list is held out and not judged. There is no verdict, score or rank in a word or a field name, and a test holds that.

## 4. What it does not do

- It does not count agents that exist, work or are active. It counts entries the directory lists.
- It does not rank chains or registries, and gives no per-agent figure.
- It does not show a held-out registration or say why one is held out beyond the published rules.

## 5. Checks

- `server/apiStats.test.ts` (11 tests): the three reads put together, a failed read failing, a chain that is not served left out, an extra chain's registrations, BNB Chain's from its own read, null kept apart from zero, and the statement.

## 6. Open

- The developer page has a card for the endpoint, with a curl and a JavaScript example.
- `/api/v1/chains` as a separate answer is not built, by the choice above.
- Ethereum joins the rows when its switch goes on. Stage 5 of the operator's plan is not started.
- `scripts/verify-live.mjs` does not call the endpoint. The comparison in section 7 was a one-off script outside the repository, so a later regression would show only in a caller's own check.
