## 1. What this adds

Monad (chain id 143) joins Ethereum, Base and Arc as an entry in the one chain list (`server/ingestion/erc8004Chains.ts`, `MONAD_CHAIN`), behind its own switch, `chain_monad`. The pass, the decoding, the listing rules and the flood cap are the ones those chains use ([the multichain record](./multichain-erc8004-2026-10-20.md)); this change adds the entry and the places a chain has to be named:

| Where | What |
|---|---|
| `server/ingestion/erc8004Chains.ts` | `MONAD_CHAIN` and `MONAD_LISTING_RULES` (BNB Chain's numbers, provisional until a census, like the other chains'), added to the list |
| `shared/chains.ts`, `shared/features.ts` | the extra chain `monad`, its label, its switch `chain_monad`, its protocol `erc8004_monad` |
| `server/_core/env.ts` | `MONAD_RPC_URL`, read when a run starts, never printed or stored |
| `drizzle/0053_monad_erc8004_protocol.sql`, `drizzle/schema.ts`, `server/ingestion/types.ts` | the protocol value on the four tables that carry the list (by hand, section 6) |
| `server/ingestion/worker.ts`, `server/routers/liveData.ts` | the scheduled dispatch (it still refuses a source that is not on the scheduler) and the staging action, with a clear message when 0053 has not been pasted |
| `server/apiChains.ts` | the API chain `monad`, served while the switch is on |
| `client/src/components/home/chainTabsModel.ts`, `client/src/index.css`, `client/src/lib/glossary.ts`, `client/src/pages/SourceOperations.tsx` | the tab (a four-pointed star, rose), "seven skies" in the heading when all the switches are on, the operator page's button and label |
| `client/src/components/home/constellationModel.ts` | the map's chain type leaves Monad out, because it has no lights yet |

With the switch off nothing of Monad is listed, counted, served or run, exactly as for the other extra chains. Off is held in one place: the visibility rule every directory read shares ends with a `NOT IN` over the protocols of the chains that are off.

## 2. What the real chain held (read on 2026-11-01)

- **The same contract.** The identity registry at `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` is the same 130-byte proxy as on every chain (same SHA-256 of the code as Ethereum's), and its implementation, `0x7274e874ca62410a93bd8bf61c69d8045e399c02`, has the same 14,474 bytes of code as Ethereum's. So the decoding is shared, and a chain is an entry. The contracts README of the registry's authors and Monad's own guide name it.
- **Where it starts.** Deployed at block 52,952,790 (2026-02-03 11:36:02 UTC), found by binary search on `eth_getCode` (empty at 52,952,789, 130 bytes at 52,952,790) on two archive nodes. The first registration is at block 53,006,722 (2026-02-03 17:35 UTC). The head was 118.3 million blocks, so the registry's history is 65.4 million of them.
- **How fast it moves.** 0.3021 s a block over the last million blocks, so an hour is 11,918 blocks. The `finalized` tag is served and sat 2 blocks behind the head.
- **What it holds.** 10,420 registrations, ids 0 to 10,419 (counted from the events, and the highest id that has an owner agrees). The first id is 0, which the decoder reads like any other. 8004scan lists 10,337 agents on Monad. The three kinds of event the pass asks for number 21,047: 10,420 `Registered`, 10,506 `Transfer` (10,420 mints and 86 hand-overs) and 121 `URIUpdated`. The registry emits two more kinds the pass does not ask for (12,111 and 10,466 of them), so a read of every log from the address is 43,661.
- **When.** Read in 1,308 windows of 50,000 blocks (65 s through the keyed endpoint, none failed), only 301 hold an event of the three kinds, with a median of 4. The eight busiest hold 17,474 of the 21,047: six consecutive windows from block 55,702,790 to 56,002,789 (16 February 06:32 to 17 February 15:57 UTC) and two on 2 and 3 July (blocks 85,102,790 to 85,302,789). The busiest has 2,944 events and is 2.2 MB as JSON. 8004scan counts no new Monad agent a day.
- **What providers allow** (`eth_getLogs`, read 2026-11-01). By Monad's own table the public nodes allow 100 blocks (QuickNode's and the Monad Foundation's), 1,000 blocks and 10,000 logs (Alchemy's) and 1,000 blocks (Ankr's). A probe on 2026-11-01 found Alchemy's public node refusing 1,000 blocks, Ankr's serving no old state, and one node the table does not list (`rpc2.monad.xyz`) allowing 10,000 blocks and serving old state. The keyed Alchemy endpoint the Base pass already uses answered 20,000 blocks in the busiest stretch and 500,000 in a quiet one, and archives to the deploy block. Its own rule, in the words of the refusal recorded in the fixtures: up to 1,000 blocks with no limit on the response size, or any range with a cap of 10,000 logs in the response. The pass reads windows of 50,000 blocks, whose busiest holds 2,944 events, so the cap is not reached.

## 3. Who registered (chain facts as recorded, not judged)

- 10,133 of the 10,420 registrations carry a web link, 93 a raw JSON string (an unrecognized scheme), 89 inline JSON, 85 an empty URI and 20 an IPFS link.
- The web links name 41 hosts. One host holds 8,094 registrations (78%), and the next four 762, 528, 483 and 51. There are 8,686 registering wallets; 8 of them registered 10 or more (1,484 registrations). There are 2,129 distinct profile links, 33 of them shared by two or more registrations (8,324 registrations).
- The listing rules treat a shared link, a host with 50 or more registrations and a wallet with 10 or more as one group, not as agents, and the flood cap stores at most 2,000 rows for a host. Those numbers are what put the listing near 1.4% of the registry (section 5). Before the rehearsal the listing was estimated at 500 to 1,500, from the share the other chains list (1% to 14%); the rehearsal found 144, because this registry is concentrated in a few hosts.

## 5. The rehearsal

The real pass, with the budget in the entry, against a scratch MariaDB 10.11 and the real chain through the keyed endpoint, from the deploy block to the finalized head, the way the operator's "Run chain pass" button will:

- 16 runs, 47 seconds of runs in all, the longest 4.9 s. The first read 59 windows (2.95 million blocks) and applied 11,569 events (a run stops after the window that takes it past 10,000), runs 2 to 13 each read 100 windows (5 million blocks), the 14th read the last 49 windows, reached the head (cursor `monad:118346118`) and published, and the 15th and 16th found nothing to do.
- 21,047 events accepted, equal to the offline count of section 2.
- 4,326 registry rows stored. 6,094 registrations were counted and not stored, all for the one host past the flood cap (2,000 of its registrations are stored). Of the stored rows, 169 have no usable link, 144 are listed and 4,013 are grouped.
- **144 entries published**, of 10,420 registrations (1.4%). 95 of them are named `Agent #n` and 62 have a host; the names step does not read Monad yet (section 7).
- 4,326 mints, 86 hand-overs and 121 URI updates in the ledger. About 16 MB of tables in all (registry rows 9.7, ledger 5.8), and a process that stayed under 175 MB.
- The first pass is about fourteen presses of the button, or the scheduler's own ticks if the source is flipped first.

## 6. The operator's steps

Each step's file was given to the operator as a paste-safe copy.

0. **Read the migration log.** `0053_log_check.sql` shows the last six rows of `nooscape_schema_migrations`. Version 53 must not be there; if it is, say so and the number changes (a version already recorded is skipped, which once lost migration 0047).
1. **Migration 0053, by hand, at a quiet moment** (not on a worker tick: :00, :15, :30, :45). It appends `erc8004_monad` to the protocol list of four tables. It needs 0046 and 0051, which production has, because every statement restates the whole list.
   - Run `0053_check.sql` first: each of the four rows must end with `'erc8004_arc','solana_agenc')`.
   - Paste `0053_monad_erc8004_protocol.sql`. Run `0053_check.sql` again: each row now ends with `'solana_agenc','erc8004_monad')`.
   - Record it with `0053_record.sql`. The name must be exactly the file's: a version recorded under another name stops the next boot.
   - Rollback is `0053_rollback.sql`: the first query counts the rows that hold the value and every count must be 0; then the same four statements with the earlier list, and the version is deleted.
   - Staging the source before the file is pasted answers "The database does not have the Monad protocol value yet. Paste migration 0053 first", and creates nothing.
2. **Set `MONAD_RPC_URL`** on the host to the Alchemy Monad address. The pass accepts only the host `monad-mainnet.g.alchemy.com`. Do not change the repository settings of the app (that wipes the environment).
3. **Add `chain_monad` to `VITE_FEATURES`**, keeping the value it has (`claims,chain_arc,claims_arc,chain_base,chain_ethereum` on 2026-10-28), and redeploy once.
4. **On /admin/sources**: Stage Monad ERC-8004 registry, approve it, press Run chain pass until the run that follows one that moved the cursor finds nothing (about fourteen presses).
5. **Check**: the tab shows "Monad" with the chain's figures, `GET /api/v1` lists `monad`, `node scripts/verify-live.mjs` passes. A manual-only source is not held to a freshness allowance, so `verify-live` stays green.

Rollback of the whole change: remove `chain_monad` from `VITE_FEATURES` and redeploy. Monad then disappears from every read, and the source can be paused.

## 10. The scheduled flip (migration 0054)

The source `monad-erc8004-identity-registry` has been `manual_only` since the go-live, so nothing reads the registry's new registrations and the chain's figures stay as of the last manual pass (03:27Z on 2026-11-01). Migration 0054 hands it to the scheduler once a day, the way 0050 did for Arc and 0052 for Ethereum. The operator asked for it on 2026-11-01 ("do the scheduled refresh first", from the list of what Monad still lacks).

- **What it is.** One guarded UPDATE that names no protocol, applied at boot like 0050 and 0052. It changes the source only if it is the approved Monad source by its key, active, still `manual_only`, holding a `monad:` cursor, with a recorded success and no recorded failure. Then it sets `scheduled`, 1440 minutes, due now. Run again, or on a database where the source is not in that state, it changes nothing. `server/monadScheduledFlip.test.ts` tests each guard against a real MySQL (and MariaDB 10.11), and eleven planted changes to the file and the live check are each caught.
- **What the pass reads.** The pass itself is unchanged: chain facts from finalized blocks through the keyed `MONAD_RPC_URL` endpoint, windows of at most 50,000 blocks, up to three at a time, a run bounded to 100 windows, 30 seconds and 10,000 events, no URI fetched and no reviewed record added. A day is about 286,000 blocks (0.3021 s a block), six windows. The registry is nearly still: through the keyed endpoint it recorded 3 events of the three kinds in the day to 14:59Z on 2026-11-01 (one registration), against 21,047 in all and 2,944 in the busiest window. One run a day has room. The pass does not start while the `chain_monad` switch is off.
- **At the deploy.** The migration runs at the first boot, the source is due at once, and the worker's next tick (every 15 minutes) claims it. The first run reads from the stored cursor, where the manual pass stopped, to the finalized head, a few windows. The next is due a day after it finishes.
- **The live check.** `scripts/verify-live.mjs` gets `erc8004_monad: 36`, so a scheduled Monad source that has not succeeded within 36 hours fails the check. Between the deploy and the end of the first run the source still shows its old success, so run the check again after the first tick.
- **What changes on the site.** The Monad tab's "Last successful read of this chain" moves each day, and a registration that appears is listed, under the listing rules, within a day. Nothing else changes.
- **The migration number.** The boot runner refuses to start when a version is recorded under another file's name, so the number was checked against the operator's migration log before the merge. On 2026-11-01 it showed versions 50 to 53 recorded under the same file names as the repo and nothing at 54.
- **Rolling back.** Set the source back to operator-paced with `UPDATE ingestion_sources SET executionPolicy = 'manual_only' WHERE sourceKey = 'monad-erc8004-identity-registry';`. The cursor is not touched.
- **What happened.** Merged as PR 239 at 16:34:44Z on 2026-11-01 (main `d0165cf`), after the gate had passed on the same commit. The deploy was at 16:35:29Z, and the source read `scheduled` from 16:35:57Z, so the migration ran at the first boot and nobody ran SQL. `verify-live` read 48 passed, 0 warnings, 0 failed, one more than before: the new line is the Monad source's "ran recently" (13.2h ago against the limit of 36h). The first scheduled run finished at 17:15:08Z, the third tick after the deploy: the worker takes at most two due sources a tick, oldest first, and four other sources ran ahead of Monad at 16:45 and 17:00 (Ethereum's first run waited two ticks the same way). The source's last success moved from 03:27:21Z (the manual pass) to 17:15:08Z, `registrations_on_chain` from 10,420 to 10,421 and `acknowledged` stayed at 144, with no failure, and `verify-live` read 48 of 48 again after it (the Monad line "ran recently: 0.0h ago"). The evidence is the source's public status row, the live check, the stats API and the runtime log. The log's boot line at 16:35:57Z reads "Applied 1 pending: 0054_monad_scheduled_flip.sql". It holds no line from the 17:15 run, which fits a run that listed nothing (the pass logs only when it adds, refreshes or removes a listing), and no warning of a failed listing refresh.
- **Chosen by Claude, so the operator can say no.** Once a day, as Arc's and Ethereum's are, and the 36-hour allowance the other daily sources get.
