# Gnosis: the ERC-8004 identity pass on an eighth chain

Status: **BUILT AND TESTED (2026-11-06); SWITCHED OFF; NOT STAGED.** The operator said "lets add gnosis" on 2026-11-06. Gnosis runs the same contract as Ethereum and Monad and has the smallest history of the chains left, so it was the cheap one to add next ([the Monad record](./monad-erc8004-2026-11-01.md) is the model). Nothing runs until the owner applies migration 0057 by hand, sets `GNOSIS_RPC_URL`, adds `chain_gnosis` to `VITE_FEATURES`, deploys, stages the source, approves it and runs it. The names, the copy, the MCP package, the map lights, a page, the ratings, the claims, a census and the scheduled flip are separate, later changes (section 7), as they were for Monad.

**Update, later on 2026-11-06:** live. The pull request merged at 21:07Z (PR 299, main `ba84611`) and the operator's steps were done the same hour, by Claude on the operator's order: the pass listed 41 of 4,179 registrations, as rehearsed. Section 9 has what happened.

## 1. What this adds

Gnosis (chain id 100) joins Ethereum, Base, Arc and Monad as an entry in the one chain list (`server/ingestion/erc8004Chains.ts`, `GNOSIS_CHAIN`), behind its own switch, `chain_gnosis`. The pass, the decoding, the listing rules and the flood cap are the ones those chains use ([the multichain record](./multichain-erc8004-2026-10-20.md)); this change adds the entry and the places a chain has to be named:

| Where | What |
|---|---|
| `server/ingestion/erc8004Chains.ts` | `GNOSIS_CHAIN` and `GNOSIS_LISTING_RULES` (BNB Chain's numbers, provisional until a census, like the other chains'), added to the list |
| `shared/chains.ts`, `shared/features.ts` | the extra chain `gnosis`, its label, its switch `chain_gnosis`, its protocol `erc8004_gnosis` |
| `server/_core/env.ts` | `GNOSIS_RPC_URL`, read when a run starts, never printed or stored |
| `drizzle/0057_gnosis_erc8004_protocol.sql`, `drizzle/schema.ts`, `server/ingestion/types.ts` | the protocol value on the four tables that carry the list (by hand, section 6) |
| `server/ingestion/worker.ts`, `server/routers/liveData.ts` | the scheduled dispatch (it still refuses a source that is not on the scheduler) and the staging action, with a clear message when 0057 has not been pasted |
| `server/apiChains.ts` | the API chain `gnosis`, served while the switch is on |
| `client/src/components/home/chainTabsModel.ts`, `client/src/index.css`, `client/src/lib/glossary.ts`, `client/src/pages/SourceOperations.tsx` | the tab (teal; a hexagon when the chain went live, an octagon since 2026-11-06 because Robinhood Chain's lights are hexagons, see [the page](./gnosis-world-2026-11-06.md)), "eight skies" in the heading when all the switches are on, the operator page's button and label |
| `client/src/components/home/constellationModel.ts` | the map's chain type leaves Gnosis out, because it has no lights yet |

With the switch off nothing of Gnosis is listed, counted, served or run, exactly as for the other extra chains. Off is held in one place: the visibility rule every directory read shares ends with a `NOT IN` over the protocols of the chains that are off.

## 2. What the real chain held (read on 2026-11-06)

- **The same contract.** The identity registry at `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` is the same 130-byte proxy as on every chain (the code's SHA-256 prefix `e3b1c1b4c04b34f9` equals Ethereum's, Monad's, Abstract's and 0G's), and its implementation, `0x7274e874ca62410a93bd8bf61c69d8045e399c02`, has the same 14,474 bytes (prefix `201b7634af2de088`). So the decoding is shared, and a chain is an entry. The reputation registry at `0x8004BAa17C55a88189AE136b182e5fdA19dE9b63` is deployed too (a 130-byte proxy); its ratings are not read here (section 7).
- **Where it starts.** Deployed at block 44,505,010 (2026-02-04 09:49:00 UTC), found by binary search on `eth_getCode` through the keyed endpoint (empty at 44,505,009, 130 bytes at 44,505,010), which archives to it. The first registration is at block 44,506,402. The finalized head sat 40 blocks behind the head at 49,144,785, so 4,639,735 blocks of history.
- **How fast it moves.** 5.0827 s a block over the last 100,000 blocks, so an hour is 708 blocks. The `finalized` tag is served.
- **What it holds.** 4,179 registrations, ids 0 to 4,178 (counted from the events). 8004scan lists 4,171 agents on Gnosis. The three kinds of event the pass asks for number 8,412: 4,179 `Registered`, 4,184 `Transfer` (4,179 mints and 5 hand-overs) and 49 `URIUpdated`. The registry emits more kinds the pass does not ask for (20,203 and 4,206 of them), so a read of every log from the address is 32,826.
- **When.** The launch burst: 2,807 of the registrations were made in February, 2,652 of them in the first 10,000 blocks (about 14 hours). Since then it is quiet: 518 in March, then 109, 127, 254, 289, 17, 29 and 27 a month, and 2 in November (months interpolated from the first and last block times). The last log of any kind is from 2026-11-04.
- **What the provider allows** (`eth_getLogs`, the keyed Alchemy endpoint the Base and Monad passes use, read 2026-11-06). At most **10,000 blocks** a call, with no cap on the response: the first 10,000 blocks returned 21,217 logs of every kind (18 MB). A wider window is refused with an HTTP 400 that reads "You can make eth_getLogs requests with up to a 10000 block range. Based on your parameters, this block range should work: [...]" (the real refusal is in the recording, section 8). The pass classifies that as a block-range fault, because its planner never asks for more than the entry's `maxLogRange`. Monad's endpoint, by contrast, allowed 50,000 blocks while the response held 10,000 logs or fewer.
- **The three kinds, by window.** Read as 10,000-block windows, 238 of the 464 hold an event of the three kinds, with a median of 4 and a 90th percentile of 22. The busiest is the launch, blocks 44,505,010 to 44,515,009: 5,304 events, 4.0 MB as JSON (779 bytes an event); the next busiest holds 202.

## 3. Who registered (chain facts as recorded, not judged)

- 3,891 of the 4,179 registrations carry a web link, 265 inline JSON, 22 an empty URI and 1 an IPFS link. One of the inline JSON texts is gzip-compressed (a `data:` link with `enc=gzip`); the pass does not read compressed JSON, so it counts as inline JSON that did not parse and is held out, as the listing rules say.
- The web links name 7 hosts. One host, the Olas marketplace, holds 3,851 registrations (92%); the next holds 32.
- There are 52 registering wallets. One made 3,851 registrations, 26 made 10 or more (4,136 in all), and the next four made 34, 18, 12 and 11. There are 4,140 distinct links, 10 of them shared by two or more registrations (27 registrations).
- The listing rules treat a shared link, a host with 50 or more registrations and a wallet with 10 or more as one group, not as agents, and the flood cap stores at most 2,000 rows for a host. Those numbers are what put the listing at about 1% of the registry (section 5).

## 5. The rehearsal

The real pass, with the budget in the entry, against a scratch MariaDB 10.11 and the real chain through the keyed endpoint, from the deploy block to the finalized head, the way the operator's "Run chain pass" button will:

- 6 runs, 43 seconds of runs in all, the longest 11.4 s. The first read 100 windows (the first million blocks, with the launch) and applied 6,730 events; runs 2 to 4 each read 100 windows; the fifth read the last 64 windows, reached the head (cursor `gnosis:49145026`) and published; the sixth found nothing to do.
- 8,412 events accepted, equal to the offline count of section 2.
- 2,328 registry rows stored. 1,851 registrations were counted and not stored, all for the one host past the flood cap (2,000 of its registrations are stored). Of the stored rows, 9 have no usable link, 41 are listed, 2,277 are grouped and 1 has a name that is only a number.
- **41 entries published**, of 4,179 registrations (1.0%). 10 of them are named `Agent #n` and 6 have a host.
- 2,328 mints, 5 hand-overs and 49 URI updates in the ledger. About 8 MB of tables in all (registry rows 4.3, ledger 3.6, entries 0.2), and a process that stayed under 155 MB.
- The first pass is five presses of the button, or the scheduler's own ticks if the source is flipped first.

## 6. The operator's steps

Each step's file was given to the operator as a paste-safe copy (`0057_log_check.sql`, `0057_check.sql`, `0057_gnosis_erc8004_protocol.sql`, `0057_record.sql`, `0057_rollback.sql`). Production has run on its own server since 2026-11-06; its database is the `db` container of its stack.

0. **Read the migration log.** `0057_log_check.sql` shows the last six rows of `nooscape_schema_migrations`. Version 57 must not be there (on 2026-11-06 the newest was 56, `0056_listing_pins.sql`); if it is, say so and the number changes (a version already recorded is skipped, which once lost migration 0047).
1. **Migration 0057, by hand, at a quiet moment** (not on a worker tick: :00, :15, :30, :45). It appends `erc8004_gnosis` to the protocol list of four tables. It needs 0046, 0051 and 0053, which production has, because every statement restates the whole list.
   - Run `0057_check.sql` first: each of the four rows must already end with `'solana_agenc','erc8004_monad')`.
   - Apply `0057_gnosis_erc8004_protocol.sql`. Run `0057_check.sql` again: each row now ends with `'erc8004_monad','erc8004_gnosis')`.
   - Record it with `0057_record.sql`. The name must be exactly the file's: a version recorded under another name stops the next boot.
   - Rollback is `0057_rollback.sql`: the first query counts the rows that hold the value and every count must be 0; then the same four statements with the earlier list, and the version is deleted.
   - Staging the source before the file is applied answers "The database does not have the Gnosis protocol value yet. Paste migration 0057 first", and creates nothing.
2. **Set `GNOSIS_RPC_URL`** in `app.env` on the server to the Alchemy Gnosis address. The pass accepts only the host `gnosis-mainnet.g.alchemy.com`.
3. **Add `chain_gnosis` to `VITE_FEATURES`** in the stack's `.env`, keeping the value it has, and deploy (`bash deploy.sh $(cat .deployed)`, because the list is read when the site is built).
4. **On /admin/sources**: Stage Gnosis ERC-8004 registry, approve it, press Run chain pass until the run that follows one that moved the cursor finds nothing (about five presses).
5. **Check**: the tab shows "Gnosis" with the chain's figures, `GET /api/v1` lists `gnosis`, `node scripts/verify-live.mjs` passes. A manual-only source is not held to a freshness allowance, so `verify-live` stays green.

Rollback of the whole change: remove `chain_gnosis` from `VITE_FEATURES` and deploy. Gnosis then disappears from every read, and the source can be paused.

## 10. The scheduled flip (migration 0058)

The source `gnosis-erc8004-identity-registry` has been `manual_only` since the go-live, so nothing reads the registry's new registrations and the chain's figures stay as of the last manual pass (21:12Z on 2026-11-06). Migration 0058 hands it to the scheduler once a day, the way 0050 did for Arc, 0052 for Ethereum and 0054 for Monad. The operator asked for it on 2026-11-06 ("lets go fully live with gnosos once you have all you need to do it", from the list of what Gnosis still lacks).

- **What it is.** One guarded UPDATE that names no protocol, applied at boot like 0050, 0052 and 0054. It changes the source only if it is the approved Gnosis source by its key, active, still `manual_only`, holding a `gnosis:` cursor, with a recorded success and no recorded failure. Then it sets `scheduled`, 1440 minutes, due now. Run again, or on a database where the source is not in that state, it changes nothing. `server/gnosisScheduledFlip.test.ts` tests each guard against a real MySQL (and MariaDB 10.11), including that it names no protocol and that a source with a key close to the approved one and a Gnosis cursor is left alone, and twenty-two planted changes to the file, the live check and the names and ratings work are each caught.
- **What the pass reads.** The pass itself is unchanged: chain facts from finalized blocks through the keyed `GNOSIS_RPC_URL` endpoint, windows of at most 10,000 blocks, up to three at a time, a run bounded to 100 windows, 30 seconds and 10,000 events, no URI fetched and no reviewed record added. A day is about 17,000 blocks (5.08 s a block), two windows. The registry is nearly still: through the keyed endpoint it recorded no event of the three kinds in the 17,000 blocks to 2026-11-06 (4 in the week and 48 in the month, half of them registrations), against 8,412 in all and 5,304 in the busiest window. One run a day has room. The pass does not start while the `chain_gnosis` switch is off.
- **At the deploy.** The migration runs at the first boot, the source is due at once, and the worker's next ticks (every 15 minutes) claim it; the worker takes at most two due sources a tick, so a freshly flipped source can wait two or three ticks. The first run reads from the stored cursor, where the manual pass stopped, to the finalized head, a few windows. The next is due a day after it finishes.
- **The live check.** `scripts/verify-live.mjs` gets `erc8004_gnosis: 36`, so a scheduled Gnosis source that has not succeeded within 36 hours fails the check. The status page keeps a copy of the limits (`client/src/lib/statusModel.ts`), and a test holds it equal to the script's, so it gets the same line. Between the deploy and the end of the first run the source still shows its old success, so run the check again after the first tick.
- **What changes on the site.** The Gnosis tab's "Last successful read of this chain" moves each day, and a registration that appears is listed, under the listing rules, within a day. Nothing else changes.
- **The migration number.** The boot runner refuses to start when a version is recorded under another file's name, so the number was checked against production's migration log on 2026-11-06, read over ssh: versions 57 down to 52 recorded under the same file names as the repo (57 is `0057_gnosis_erc8004_protocol.sql`, applied at 21:08Z) and nothing at 58. No other pull request was open.
- **Rolling back.** Set the source back to operator-paced with `UPDATE ingestion_sources SET executionPolicy = 'manual_only' WHERE sourceKey = 'gnosis-erc8004-identity-registry';`. The cursor is not touched.
- **Chosen by Claude, so the operator can say no.** Once a day, as Arc's (until 2 November), Ethereum's and Monad's are, and the 36-hour allowance the other daily sources get.
