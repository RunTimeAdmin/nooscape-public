# Claim this agent, for Celo

The claim flow ([docs/claims-2026-10-18.md](./claims-2026-10-18.md)) opened to the owners of agents on Celo, the way it was opened to [Arc's](./arc-claims-2026-10-20.md), [Base's and Ethereum's](./base-ethereum-claims-2026-10-28.md), [Monad's](./monad-claims-2026-11-01.md) and [Gnosis's](./gnosis-claims-2026-11-06.md). One new switch, one chain entry, one node for the claim reads built from the shared module, and a few lines in the flow and the page. No migration, no new table and no new setting: it uses the three claim tables (migration 0042) and the endpoint the Celo identity pass already reads (`CELO_RPC_URL`, the Celo Foundation's public node at `forno.celo.org`, which takes no key).

The same route carries the check's `pay_to` read ([docs/check-pay-to-2026-11-20.md](./check-pay-to-2026-11-20.md)). `getAgentWallet` goes through `callChain`, so until this change a `pay_to` for a Celo agent came back "not read", and it now reads the registry.

**Status.** Built on 2026-11-20 on branch `feat/celo-claims`, the fifth of the six stages and stacked on the census. **The claims are off until the operator adds `claims_celo` to `VITE_FEATURES`.** Merging this opens them to no one. Production reads `claims,chain_arc,claims_arc,chain_base,chain_ethereum,chain_monad,chain_gnosis,chain_celo` (read from the live build on 2026-11-20): Arc's claims are on, and the claims of Base, Ethereum, Monad and Gnosis are off, so Celo's stay off with them unless the operator says otherwise. The `pay_to` read needs no switch of its own: it works once this is deployed, for as long as `chain_celo` is on.

**Decided:** 2026-11-20, by the operator, in chat: "all in order" (the fifth of the six stages, `pay_to` and claims for Celo). The shape of the answer is mine, chosen to follow Gnosis's claims, so the operator can say no to any of it.

## The switch

`claims_celo` (`shared/features.ts`). Agents on Celo can be claimed only while **`chain_celo` and `claims_celo` are both on**; the panel itself is still `claims`. No other chain's switches open it, and its switches open no other chain. To open it: add `claims_celo` to `VITE_FEATURES` and rebuild and restart. On the server that is the line in the stack's `.env` and `bash deploy.sh $(cat .deployed)`, because the page needs the build and the server the restart, and both read the same list. Taking it out again closes it.

The reason for a switch of its own is Arc's: the flow asks for a signature, reads a chain to decide who owns an agent, and the Privacy page says what it does. Celo's page, census, lights and ratings go live with their merges, and its claims go live when the operator has read this and decided to.

## What changes

- **The chain.** `CLAIM_CHAINS` gains Celo (chain id 42220, label "Celo") with the identity registry's address. `claimChainOf(protocol)` returns it only while its two switches are on, so everything that asks "can this be claimed?" (the entry lookup, the message, the page's state, the daily check) answers no for an agent on it while they are off, with the words it uses for any entry that cannot be claimed.
- **The words for an entry that cannot be claimed** name the registries that can, in the order Robinhood Chain, BNB Smart Chain, Arc, Base, Ethereum, Monad, Gnosis, Celo, each only while its claims are on.
- **The message to sign** is the same sign-in text, with `Chain ID: 42220` and the registry and token as its resource (`eip155:42220:<registry>:<token>`). Nothing else in it changes.
- **The entry.** An agent can be claimed only if the public can see it, as for the others, so a registration the listing rules hold out has no claim. On Celo that is most of them: 517 of the 10,080 registrations are listed ([the census](./celo-census-2026-11-20.md)). The key must name exactly the chain's registry on the chain.
- **The fleet rule** counts the visible entries of the wallet, and of the wallet the entry was registered by, on the same protocol, as for the others. Celo's listing rules hold out a wallet that registered 10 or more, so an agent that is listed is from a wallet that registered fewer than 10, and the fleet rule (50) will not bite.
- **The agent's page** already has a colour for Celo (`erc8004_celo`, the tab's green), added with the page.

## The read of the chain

A claim asks the chain three things and nothing else: who owns the agent now (`ownerOf`), whether a wallet is a contract (`eth_getCode`) and whether a contract wallet accepts a signature (EIP-1271, `eth_call`). They go to the endpoint the chain's pass reads, through `server/claimsPinned.ts`, which now builds a fifth node from `server/claimsNode.ts`:

- **The checks** are the shared module's: the node answers as the chain (`eth_chainId`), it is at the head (a latest block no more than ten minutes old, and not dated more than two minutes ahead of the server's clock), one attempt with no retry ladder, and a gas limit on what a visitor can make it run (200,000 for `ownerOf`, 3,000,000 for anything else). A failed check is fixed text that can never be read as a revert.
- **The address** is read as the pass reads it: `CELO_RPC_URL` must be set, an https address with no credentials in it, and its host must be exactly the host the chain's entry pins (`forno.celo.org`), so changing the variable can never send a claim's reads to a host nobody approved. Celo's node takes no key, so unlike the others' the address holds none, but it is held the same way: nothing puts it in an error or a log line, and an address that is not usable is "not configured" in fixed words. The host is a public service's, pinned in the code, so it is not looked up again.
- **The same budget as the others.** A visitor's reads of a chain are held to 60 a minute and refused as "try again" past that, without asking the node; the daily check has no such cap. A revert (a token that does not exist, answered in the EVM's own words) is an answer: no owner. A missing method, a throttle or a timeout is an outage and can never end a claim.
- **The provider's bill.** A read costs the node one call, and up to two more when the chain id (asked once in ten minutes) or the head (once a minute) is due. A visitor is held to 60 reads a minute and the daily check takes at most 25 claims a run. The node is the Celo Foundation's free public one, whose limits are not published, so no limit was checked against that here. The endpoint is also read by the identity pass (one run a day, to 3 windows at a time) and by the ratings step.
- **Checked against the real chain** on 2026-11-20, read-only, through the flow's own client and route (`callCeloRpcOnce` and `callChain`): the node answered as chain 42220 and its latest block passed the head check; `ownerOf` of three registrations (the first, a middle one and the newest the registry holds) each answered one address; `ownerOf` of an id that was never registered reverted and came back as "no owner"; `eth_getCode` answered code for the registry and none for an address with no code; and the claim chain is claimable with both switches on and not with `chain_celo` alone.
- **Checked on the real server** on 2026-11-20, with a build that had `claims_celo` on, a scratch database holding Celo's real rows and the three claim tables, and the real node: the claim state of a listed Celo entry is available and claimable; the message issued for a wallet carries `Chain ID: 42220` and the resource `eip155:42220:<registry>:<token>`; the agent's page shows the panel ("If you own this agent's registration on Celo, you can claim it") with its connect button; and the Privacy page carries Celo's sentence and the date 20 November 2026. No console error. The ownership read that happens when a signature arrives was not exercised there, because no wallet signed; the chain reads above are the same ones.

## The check's `pay_to`

`getAgentWallet(agentId)` went through the same route, so the check's `pay_to` now answers for a listed Celo agent (the API already served Celo's agents). Read through the route on 2026-11-20: two registered ids each answered a wallet, and an id nobody registered answered "none" and did not revert, as on the other chains.

A seeded draw of 100 registered ids (the seed `20261120`, ids 0 to 10,079, each id's owner and wallet read through the claim route's worker variant) found 27 whose wallet is the owner, 72 whose wallet is another address and 1 with none. So on Celo the usual answer is that the registry holds a wallet and it is not the owner's, the opposite of Base, Arc, Robinhood Chain and Gnosis, where most agents hold none. The row is in [the `pay_to` record](./check-pay-to-2026-11-20.md).

## The daily check

Unchanged from the other chains': it selects only claims on a chain whose claims are on, and a chain that cannot be read is left out for the rest of the run so the claims behind it on other chains are still asked about. A claim made on Celo while its switch was on is kept when the switch goes off and is checked again from the day it returns.

## What the pages say

- **Terms.** Unchanged: "the owner of an agent in a public registry" already covers it.
- **Privacy.** The sentences that name the chains are untouched, and **one sentence is added only while Celo's claims are on in the build**: "The owner of an agent on the Celo registry can claim it in the same way." The page's date reads 20 November 2026 while it is there, and otherwise the older dates, because the text it describes is the text on the page. This is the only legal wording the change touches, and it adds a chain to a list rather than a clause. The operator's review of it is the open point.
- **The panel** says "If you own this agent's registration on Celo, you can claim it", in the other chains' words, on an agent's page while its switches are on, and is not there otherwise.

## What does not change

A claim is still the owner's own word and never a tier, a review, a rating or a score. It changes nothing about whether a Celo registration is listed, where it sits, any count, the page, the census, the lights or the ratings. The flow still cannot write a field it does not own, and the claim code still names no tier, state, listing flag or score. Payment has no part in it.

## Held by a test

- `features.test.ts`: the switch list, and `celoClaimsOn` (the chain and its claims named, in any case or order, each alone not enough, and the other chains' switches opening neither way).
- `claimsChain.test.ts` (Celo is a fifth row of the table that holds Base, Ethereum, Monad and Gnosis): the chain's id, registry and label; claimable only while both switches are on and no other chain's switches open it; the production call (the node's client called once, a revert from the node's own words, a timeout or HTTP error or throttle as an outage, the worker's call with no budget, a visitor's reads held to 60 a minute); and all the chains' claims together in the order the words name them.
- `claimsPinned.test.ts` (Celo is a fifth row): one request to the address in the variable, no redirect followed, no look-up of the host, the gas limits, a revert in the node's words, no address or key in anything thrown, a refusal when the variable is unset, is not https, carries credentials or names a host nobody approved, the chain id asked first and the head looked at, every failed check being fixed text, and the nodes keeping their own checks (Gnosis's being right says nothing of Celo's). The test gives the address a path that stands for a secret, because only the host is pinned; Celo's real address has none.
- `claims.integration.test.ts` (real MySQL and MariaDB, real signatures, a fake chain; Celo is a fifth row, and the test pastes migrations 0051, 0053, 0057 and 0060 by hand after 0046, as production has them): the agent cannot be claimed under any partial list or another chain's switches, and the refusal names the registries; with both switches on, the message carries the chain id and the registry, the claim is written with the chain's protocol, chain, registry and token, every read is on that chain, and the page is told it can be claimed; a wallet the registry does not record as the owner is refused and the owner's edit is taken; a held-out registration, a wrong registry and a wrong chain's key are not claimable; and the daily check ends a claim when the chain shows a new owner.
- `claimFlow.test.ts`, `legalPages.test.ts` and `claimClient.test.ts`: the panel names Celo only while both of its switches are on in the build, the Privacy sentence is conditional and its date goes with it, the claim code and the page ask the same question, and the switch list is the one the client reads.
- Planted bugs: 19 planted changes, each caught: 18 by a test and one (the fleet rule's count refusing a Celo registrant, which is a type) by the type check. They were Celo missing from the claimable list; its claims opened by Gnosis's switches, by the chain's switch alone or by the claims switch alone; its chain id read from Gnosis's entry; a registry address that is not the registry's; another label; its read sent to Gnosis's node or given no route at all (which would fail the claims and the `pay_to` read together); its node pinned to Gnosis's entry or named Gnosis; a check of Celo's node outliving a test; a flow that names Celo Gnosis or opens it on Gnosis's switches; a Privacy page without the sentence, with the old date, or with the sentence on Gnosis's switches; and a switch missing from the list. Reading the registry from Gnosis's entry cannot differ, because the registry is one address on every chain, so a literal that is not the registry stands in for it.

## Not checked, and left as it is

- **No claim was made by a real wallet on Celo.** No wallet was connected here. The signature, nonce and ownership logic is the flow's own and is held by the tests above; the contract's behaviour was read from the real chain as above. The first claim after the switch is on is the live check.
- **No independent review of this change.** What it adds on the claim path is small (one chain entry, one route into the shared module, one switch name, the endpoint's address check), but a review of `claimsNode.ts` would cover every chain's claims.
- **Smart-contract wallets** (a Safe) sign through EIP-1271 and are accepted when the wallet answers the magic value on the chain; a counterfactual wallet (not deployed yet) is refused, as for the others. ERC-6492 is not supported. EIP-1271 was not tried against a real contract wallet on Celo.
- **The public node's limits.** forno.celo.org is free and shared, and a throttle or an outage would show as "try again" to a visitor and never as a verdict on a claim. If claims become busy, a keyed endpoint (Alchemy does not serve Celo on the operator's account, as noted in [the Celo record](./celo-erc8004-2026-11-20.md)) or a second public node would have to be pinned in the chain's entry first.
- The two points the other chains' records leave as they are apply here as well: an operator's hold of a claim's text is still sent to a watching key as an event while the chain's claims are off, and a claim shows as active at once when its switch returns, until the daily check reaches it.

## To turn it on, and off

1. Add `claims_celo` to `VITE_FEATURES` in the stack's `.env` on the server (it reads `claims,chain_arc,claims_arc,chain_base,chain_ethereum,chain_monad,chain_gnosis,chain_celo` today, so the line becomes `...,chain_celo,claims_celo`) and run `bash deploy.sh $(cat .deployed)`. Read the Privacy sentence first.
2. Check: an agent's page on Celo shows the panel; `claim.state` for it says it can be claimed; the Privacy page carries Celo's sentence and the new date.
3. To stop: take the switch out and run the same deploy. Claims already made are kept and are checked again from the day it returns.
