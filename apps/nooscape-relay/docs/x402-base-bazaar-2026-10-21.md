# Base beside Arc, and the Coinbase Bazaar (21 October 2026)

Status: built on `feature/x402-base-rail`, off until two settings are set (below). Pay per call takes USDC on Base as well as on Arc: the same
address, the same prices, the same rules. Arc is still settled by Circle's Facilitator Service. Base is settled by Coinbase's CDP facilitator,
because the Bazaar, Coinbase's catalogue of paid endpoints, indexes an endpoint from a payment that Coinbase's facilitator settled and from no
other. No migration. Nothing changes for Arc or for a caller with a key.

## Why

The operator asked on 21 October 2026, "build base, i want to get on coinbase bazaar", after the directory survey showed that none of the x402
directories reads Arc: the402.dev lists Base, Solana and Ethereum, Agent402's router spends only on Base, Algorand, Solana and Tempo, and the
Bazaar needs a payment settled by Coinbase. The same day Coinbase's own validator (`POST /v2/x402/validate`, no key needed) read the live 402
and answered `valid: false`: every check passed except that `accepts[0].network` (`eip155:5042`) is not a network its facilitator supports and
that the asset is not USDC. So the Bazaar needs two things from us: a payment option on a network Coinbase settles, listed first, and one
payment that goes through its facilitator.

Circle's facilitator also settles Base, and would have been less work (same key, same retry rules). It was not used for Base because a payment
it settles never reaches the Bazaar.

## What it adds

1. **Networks as a list** (`server/x402.ts`). A `Rail` is a network with its USDC, the name the USDC signs under, the receiving address and the
   facilitator that settles it. `railsOf` gives them in the order a 402 offers them: Base first, then Arc. Base is present only when its CDP key
   is set. Everything that used to say "Arc" now asks the rail of the payment: the terms, the check of a payment against them, the signature
   check (under that network's signing domain), the payment id, the body sent to the facilitator, and the facilitator's answer.
2. **Base's terms.** `exact` USDC at `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913`, six decimals, signed under the name "USD Coin" and version
   "2". The name and version were checked on 21 October against the contract's own `DOMAIN_SEPARATOR()` (they reproduce it; "USDC" does not).
   The receiving address is Arc's, in the EIP-55 spelling Coinbase documents. It is a plain account on Base too (no code, no transactions, no
   balance on 21 October), so the same key controls it there. A payment may spell the address any way: it is compared without case.
3. **Coinbase's token** (`server/x402Cdp.ts`). Coinbase wants a JWT signed with a CDP Secret API key and made for one request. The module makes
   it from the key with `node:crypto` and installs nothing: Ed25519 (what the portal recommends, a base64 string of 64 bytes) or ECDSA P-256 (a
   PEM). It carries Coinbase's own SDK's claims, with the request named in `uris` (the SDK) and in `uri` (the examples in the docs), and lasts
   two minutes. It is sent to one address, `https://api.cdp.coinbase.com/platform/v2/x402/settle`, and never logged.
4. **The settlement call.** The body for Coinbase carries the Bazaar block we declare for the route (built here, never copied from the caller)
   and the resource, which is what Coinbase's catalogue reads on the settlement that goes through. It does not carry Circle's idempotency key.
   Its answer is sorted by what it proves about the money, as Circle's is (table below). Coinbase reports on cataloguing in an
   `EXTENSION-RESPONSES` header (`success`, `processing` or `rejected` with a reason); the server logs it with the payment.
5. **The service** (`server/x402Service.ts`). A payment is recorded under the network it names and sent to that network's facilitator. The
   same wallet and nonce on Base and on Arc are two payments. A smart-contract wallet is checked only on Arc, against Arc's node; a payment on
   Base must be signed by a regular wallet's key. The count of payments unresolved for over an hour adds up both networks.
6. **What is published.** The 402 lists Base then Arc. `/api/v1` gains `pay_per_call.networks` (each network with its USDC, address and wallets);
   the old top-level `network`, `asset`, `pay_to` and `wallets` repeat the first of them. `/llms.txt` has a line for each network. The OpenAPI
   document allows two sets of terms. The operator's payments view names both networks and adds up their totals, and each payment shows its
   network. The developer page, the Terms and the Privacy page say Base where they said Arc, and the Privacy page names Coinbase as a second
   facilitator and says it lists the API in its public catalogue (the counts it shows are of payments and of different payers).

## Settings

| Setting | What it is |
| --- | --- |
| `CDP_API_KEY_ID` | The key id the CDP portal shows (a UUID, or `organizations/.../apiKeys/...`). |
| `CDP_API_KEY_SECRET` | The key's secret. Ed25519: the base64 string. ECDSA: the PEM (a one-line setting may carry the line breaks as a backslash and an n). |
| `BASE_RPC_URL` | Optional here. The Base node the Base identity pass already reads (an https address, secret: it may carry a key). Payments use it to ask what a payer holds before a payment goes to Coinbase (see Funds and pace). Unset, or not https, Base payments go to Coinbase unchecked, as before. |

Base is on when both are set and read, and the Arc settings are for mainnet. If only one is set, or the secret is not a key, or Arc is the
testnet, Base stays off, the reason is logged (`[x402] Base is not offered: ...`, never the secret), and Arc is not affected. With the Arc
settings unset, pay per call is off as before whatever the CDP settings are.

## Switching it on (the operator's part, in this order)

1. In the CDP portal (portal.cdp.coinbase.com, a free account) open API Keys, Secret API Keys, Create API key. Choose Ed25519. If the portal
   offers permission restrictions, give the key only what the x402 facilitator needs. Leave the IP allowlist empty unless the host's outgoing address
   is known. Copy the id and the secret when they are shown: the secret is shown once.
   Before anything is deployed, check the key against Coinbase with `cdp_key_check.mts` (set the two values in one shell, run it from the app folder with
   `pnpm exec tsx`): it builds the server's own token and reads Coinbase's list of supported networks. `KEY WORKS` means Coinbase accepted the token.
2. In hPanel, add `CDP_API_KEY_ID` and `CDP_API_KEY_SECRET` to the app's environment and leave every other value as it is. Do not change the
   Git source in hPanel: on 21 October that wiped the app's environment.
3. After the deploy, the log shows `pay per call is configured for eip155:8453 and eip155:5042`. `GET https://nooscape.si/api/v1` lists both
   networks, and `POST /api/v1/check` with no body is a 402 with Base first.
4. Run Coinbase's validator on the route: `node bazaar_check.mjs` prints its verdict. It should say `valid: true`.
5. Pay once on Base, from a wallet that is not the receiving address, with `node pay_live_base.mjs <key file>` (a throwaway wallet with $1 of
   USDC on Base is enough; no ETH, the facilitator pays the gas). It refuses to sign anything but the Base terms to the receiving address under
   a price ceiling. A success shows a 200 answer, a receipt on Base and the receiving address up by 10,000 base units.
6. The catalogue takes up to about 15 minutes. `node bazaar_check.mjs` shows the route under the receiving address when it is in, and the log line
   `[x402] paid check ... on eip155:8453 (bazaar: ...)` says what Coinbase made of the metadata.

To switch Base off, remove the two settings and deploy. A Base payment still unresolved stays in the ledger and stays on the operator page and in the count of
payments unresolved for over an hour, and a caller who sends it again is told that Base is not being taken and to quote the payment id they were given. It is not
served while Base is off. Switch Base off only when none is unresolved, or look at them first.

## What Coinbase's answer means

The codes are the ones Coinbase's troubleshooting reference lists as the ones it returns in practice, sorted by whose problem each is.

| Answer | Treated as | Why |
| --- | --- | --- |
| 200, `success: true`, a transaction, our network (its id, or the older name `base`) and our payer | paid, delivered | Only a named settlement delivers. |
| `insufficient_funds`, `invalid_payload`, `invalid_exact_evm_payload_signature`, `..._authorization_value`, `..._valid_before`, `..._valid_after`, `..._undeployed_smart_wallet`, `self_send_not_allowed`, `kyt_risk_detected`, with no transaction named, at any status | refused, nothing charged | The payer's: the transfer never moved. `invalid_payload` is Coinbase's catch-all (a bad payload, a spent authorization, a failed simulation). `kyt_risk_detected` is a screened wallet. |
| `invalid_scheme`, `invalid_network`, `invalid_payment_requirements`, `invalid_amount`, `amount_too_low`, `permit2_disabled`, `preflight_validation_failed`, `invalid_bazaar_extension`, `unsupported_payload_type`, `request_blocked_by_location`, and a 400 that carries no settlement code | unavailable, nothing charged, the payment left open | Ours: our terms, our metadata, our request or the place our server is were refused. No payer can fix it, so none is told to pay again. It is logged as an error and counted as unresolved, so that it is seen. |
| 401, 402, 403 with no settlement code | unavailable, same | Our token, or our account (402: no payment method once the free 1,000 settlements a month are used), was refused. |
| `settlement_pending` (an HTTP 500 that names the transaction) | open, pending | It may still confirm. Sent once more unchanged when the caller sends the request again, as Coinbase's documentation says. |
| `settle_exact_failed_onchain`, `settle_exact_node_failure`, `settle_exact_evm_transaction_confirmation_timed_out`, `smart_wallet_deployment_failed`, `invalid_exact_evm_verification_failed`, `unknown_error`, any code we do not know, any refusal that names a transaction, 404, 409, 429, 5xx, a body that is not JSON, no answer | open | Any of these can hide a transfer. Never delivered, never refused. |

What the caller is told follows: a first send that was refused or found unavailable moved nothing, and says so. A later send is never told that nothing was charged,
because the first may have settled.

**The difference from Arc: Coinbase has no idempotency key.** Sent again, a payment that settled is refused with `invalid_payload`, which Coinbase's own reference
says looks the same as a payload that was bad to begin with. So a refusal of a send that follows an earlier send is never believed: the payment stays open, it is
not delivered and not refused, and the caller is told to check their wallet (if the USDC was not sent, sign again; if it was, quote the payment id). The same case on
Arc is served again for free, because Circle replays the settlement.

**Resolving an open Base payment** (the operator page lists it with its network, payer, amount and reason):

1. The ledger keeps the first transaction the payment named, and says in the reason when a later send named another (a re-broadcast that reverted because the first
   had spent the authorization). Look the first one up on Basescan: a confirmed transfer to the receiving address is a completed payment.
2. With no transaction recorded (an answer was lost before one was named), look at the receiving address's USDC transfers from the payer around the payment's time.
3. The answer cannot be served after the fact and this version has no refunds. A payment that did settle is closed with a note saying so; one that did not is closed
   with a note saying that.

## Staying listed

- Coinbase removes a resource that goes 30 days without a settlement, so a listing needs a paid call now and then. The latest settlement was on
  22 October 2026 (01:31 UTC), so the next is due before 21 November 2026.
- It health-probes listed routes (they must keep answering 402 with the terms to the example body) and screens the metadata for text that could
  read as an instruction to an agent. The extension block has no free text. The one free text is the route's description (`DESCRIPTIONS` in
  `server/x402.ts`): it describes the route and never addresses the caller, a test holds it to Coinbase's 500 characters, and the Bazaar's search
  reads it (see Live result). A listing that fails the screening is removed, and comes back only with another paid call.
- The validator advised an output example (`info.output`) for ranking and said it was not required for indexing; it was left out for the bytes. The 402's
  header is carried three times (the header, the body, the payment a client sends back) and Base took it from 1.9 KB to 2.2 KB. The whole response header
  block at the edge was 3,741 bytes when measured live after Base went on (this header line 2,240 of them), 3,930 after the wider description (2,460), under
  the 4 KB buffer some proxies use. A 402 that carries a long error message (a payment that could not be confirmed) is longer than the plain one by the
  difference in the message, up to about 300 bytes, and the live check measures only the plain one. AgentCash's validator then called the missing output
  schema an error, so on 22 October the block gained an output schema and an abridged example, and a payment reply drops the five headers only a document needs
  to make the room: see docs/x402-discovery-2026-10-21.md, "The output block". The test now holds the header line under 3,100 characters.

## Choices made, so the operator can say no

1. **Base first.** A client that takes the first terms it can sign pays there, most buyers hold Base USDC, and Coinbase's validator reads
   `accepts[0]`. The cost: a buyer that holds Arc USDC only and takes the first terms signs for Base, fails with no funds, and is not offered
   Arc as a fallback by a naive client. Smarter clients choose by balance. Flipping the order is one line in `railsOf`.
2. **The same address on both.** It was the operator's call and it is verified: a plain account on both chains.
3. **No smart-contract wallets on Base.** Arc's node is the only one set. A Base wallet that is a contract is told to sign with a regular key.
4. **Base only with Arc on mainnet,** so a test setup of Arc cannot offer real money on Base.
5. **Coinbase only for Base.** Arc stays with Circle, so the Circle marketplace review and the 402 for Arc are untouched (the terms for Arc are
   byte for byte what they were; only the list around them changed).
6. **A long wait for Coinbase.** The server waits 40 seconds for Coinbase's settlement answer (15 for Circle's), because Coinbase's own window is not published and
   an answer of ours that gives up first loses the transaction it would have named. The first live payments say how long it takes.
7. **The legal text changed.** Terms: "on the Arc network or, where the API offers it, on Base". Privacy: the facilitator sentence names both and
   says Coinbase lists the API in its Bazaar. A test holds the Privacy sentence to the code. These are for the operator to read; the commit that
   changes them is separate.

## Not in this

- Solana (Circle does not settle it; Coinbase does, and it needs a second payload format, no local signature check and a wider ledger: the
  payer and transaction columns are too short for a Solana address and signature). Polygon, Arbitrum and the other networks Coinbase supports.
- A check of the key at startup (the pre-flight script is the check, before deploying), and an automatic check of open Base payments against the chain. (A USDC balance
  check before a payment reaches Coinbase was added the same night: see Funds and pace.)
- Base smart-contract wallets, refunds, and a Base node to watch for reorganizations (Circle states that a Base settlement
  can be reorganized after it is reported; Coinbase's documentation did not say either way).
- Coinbase's builder-code attribution (ERC-8021).

## Live result

Base went on with the merge of PR 190 (21 October 2026, 22:52 UTC): the operator's CDP key was already set in the host.

- The key. `cdp_key_check.mts` was answered by Coinbase on all three endpoints, so the token's claims were right the first time.
- The live check (`live_base_check.mjs`) passed: the 402 offers Base first and Arc second, the response block at the edge is 3,741 bytes, the index, `/llms.txt`
  and `/.well-known/x402` list both networks, and Coinbase's validator says `valid: true` (its only advice is the output example).
- A payment on Base settled through Coinbase at 23:05 UTC: 0.01 USDC to the receiving address in transaction
  `0x8d87d4785727815f961a20b90e2ad8a9b3034f7245ce76b2342d591ce9ac7203` (block 52,917,283), with the gas paid by Coinbase's facilitator, and the answer was
  200 with the receipt. The payment script had been run twice by mistake: the same wallet paid 0.01 USDC 30 seconds earlier in
  `0x323a824b6bf5e18f6b2d95961a58e9f9ed2f40f9bd3a1626cb4243dd9e4134e2`, so the receiving address holds 0.02 USDC on Base from the two. Each run is a new
  payment, which is why the script says never to run it twice.
- The Bazaar listed `https://nooscape.si/api/v1/check` about a minute after the first payment (its documentation allows 15), with both networks and
  `quality.lastCalledAt` 23:04:42 UTC.
- Its search finds the route by the name Nooscape and by the words of its description, and not by a topic: "wallet", "agent reputation", "ERC-8004",
  "Arc USDC" and "trust check" did not return it, with up to 20 results each. The description was 83 characters and named no registry. Coinbase ranks results by
  relevance and quality, and quality counts recent calls and payers and how complete the description, output schema and metadata are. The description is now 247
  characters: it names the registry standards (ERC-8004, Solana), the three things a check takes and the four flags it returns, and says there is no score and no verdict.
  The description reaches the Bazaar in the settle call, so the next settled payment through Coinbase should replace the stored one (the payment after the deploy tests
  that), and a payment is the only way to refresh it; ranking is recomputed every six hours.

## Funds and pace (added 21 October 2026, night)

The operator pointed at the free-signature flood. An empty wallet can sign as many authorizations as it likes at no cost, and each one that reached a facilitator
took a place in the shared budget of 300 new payments a minute (our own cap, not Coinbase's), a row in the ledger and a settle call. Enough of them starve a paying
caller with "Too many payments are being started right now". Whether Coinbase counts a refused settle toward the free 1,000 a month is still not known, which is the
other reason not to send them.

- **What a new payment passes first.** `screenPayer` in `server/x402Service.ts`, before the shared budget is taken: the wallet's USDC balance on the network it pays on,
  read with one plain `eth_call` of the token's `balanceOf` (`usdcBalance` in `server/x402Chain.ts`). A regular wallet that holds less than the price is answered 402 with
  "This wallet holds less USDC than the price. Nothing was charged." Nothing is recorded and nothing is sent to the facilitator. A smart-contract wallet is not asked:
  the chain's simulation already held its funds.
- **Which node.** Arc: the operator's own, `X402_RPC`. Base: `BASE_RPC_URL`, the provider the Base identity pass already uses, so there is no new setting and no Base node
  of our own. A network with no node is not checked, and the start log says which. Neither address is put in an error or a log.
- **It never decides on a guess.** A node that fails, takes more than 3 seconds, or answers something that is not one 32-byte number lets the payment through to the
  facilitator, which decides as it always did. So does a check over its budget (1,200 a minute and 32 at once, from everyone). The node cannot make a payment succeed. It
  can only let an empty wallet be turned away early.
- **A payment already recorded is never asked again.** The check sits on the path of a new start only, so a caller whose answer was lost is served even if the wallet is
  empty by then. A refusal for funds records nothing either, so the same authorization sent again after the wallet is funded is just a new start.
- **The wallet's pace.** Once a wallet is known to hold the price it may start 60 new payments a minute on a network. The 61st is a 503 with `Retry-After: 15` and nothing
  recorded, and a payment of that wallet that is already recorded is still served. Only wallets that hold the price are counted, because the limiter keeps a table of at most
  50,000 keys and shares one budget past that, which a flood of empty wallets would have used to start refusing honest new payers.
- **What it does not stop.** Wallets cost nothing to make, so a pace per wallet does not hold against someone who signs from a new key each time. The funds check does, because
  a new key holds nothing. A flood of funded wallets pays us. A flood past the check's budget (20 a second) goes on to the facilitator as before, and the 300 a minute cap is the
  last wall. One address may make 60 payment attempts a minute, so reaching that budget takes twenty addresses. A node a few seconds behind can refuse a wallet that was funded a
  moment ago: it gets the 402 and tries again.
- **Cost and the way back.** One `eth_call` per new payment, billed by the provider at its own unit price; the budget caps the worst case. There is no switch. The way back is to
  revert the change, or to unset the node address (for Base that also stops the identity pass, so revert instead).
- **Checked live (22 October 2026).** A wallet made for the test, with nothing in it, was refused by the check on both networks in about 320 ms, with nothing recorded. The operator's
  wallet then paid (transaction `0x61fedaf16fec7a78c72ea82a651b1a52fce25a84ed401425fc93d6d27fbe69ed`) and was settled and delivered, so a funded payer passes the check through the real
  nodes (`BASE_RPC_URL` and `X402_RPC` are set and answer in production).
- **Said on the pages.** The Privacy page has one more sentence (the node provider may be asked what a paying wallet holds and sees only public chain data) and the developer page
  names both behaviours; the claims test holds the number 60 to the constant and the sentence to the code. The Privacy sentence is its own commit so the operator can change it.
