## 1. What this adds

A directory-only, chain-facts-only pass over the ERC-8004 identity registry on BNB Smart Chain (chain 56), registry
`0x8004A169FB4a3325136EB29fA0ceB6D2e539a432`, the same contract at the same address as on Robinhood Chain. At the time
of the Phase 0 verification the registry held 373,567 identities from 299,120 wallets, mostly templates and platform
issuers.

The pass stores **every** registration (D3) in its own table, `agent_directory_registry_rows`. The directory shows only
the registrations that pass published rules (section 5): 6,619 of 373,567 at the 2026-10-13 snapshot. Everything is an
acknowledgement and never a reviewed record, so no run of this source can be projected into the reviewed census. Since
2026-10-15 the home map drew a fixed sample of the listed registrations as hollow, labelled dots (section 6); PR-B3
replaced it with groups of registrations drawn as one circle each (bsc-fleet-lights-2026-10-16.md). Nothing here is a
reviewed record. That stays so: on 2026-10-17 the operator kept PR-B5 closed, so no BNB entry is promoted and none
touches the reviewed counts or the hero number (section 12).

New protocol value `erc8004_bsc` (migration `0033`, enum-only) and the registry rows table (migration `0034`, one
idempotent `CREATE TABLE`). Source key `bsc-erc8004-identity-registry`, staged `manual_only`.

## 2. What it reads, and what it does not

It makes exactly three kinds of JSON-RPC call: `eth_chainId` (must answer `0x38`), `eth_getBlockByNumber("finalized")`,
and `eth_getLogs` on the registry address with the three event topics as one OR filter: `Registered`, the ERC-721
`Transfer`, and `URIUpdated`. It sends no transaction, calls no read method on the contract, and does not look at
anything but the registry's own events.

It **never fetches an agent URI** (D2). A registration's URI is read as bytes the chain already holds: its kind, the
host of an https URI, its SHA-256, and, for inline `data:` JSON, a name decoded locally. Whether a URI resolves or
lists an endpoint is not something the worker ever learns, so nothing in this document or on the site can say that a
registration is real, and none says it is fake.

## 3. How a run works

- **One forward walk.** The cursor is `bsc:<next block>`: every block below it is done. A fresh source starts at the
  deploy block, 79,027,268 (no code at the block before it, proxy code at it). The same walk then tails the head.
- **Finalized blocks only.** The provider serves the `finalized` tag, three blocks behind `latest`, so the pass scans
  only blocks that cannot reorg and needs none of the anchor-hash machinery the Robinhood forward walk carries.
- **Windows of at most 50,000 blocks.** That is the provider's hard `eth_getLogs` ceiling (error `-32602`). From deploy
  to the measured head that is 970 windows. A run plans up to 60 consecutive windows, fetches 6 at a time, and applies
  them **strictly in chain order** however their fetches finish, so a registration is always written before the URI
  update that follows it. A window the provider calls too large is halved down to 1,000 blocks; a block-range
  rejection is a planner bug and fails the run.
- **Per-window write order.** Registry rows (INSERT-IGNORE, so a re-scan can never regress a URI a later window
  updated), then the ledger (INSERT-IGNORE, with an incremental rollup onto the registry rows), then the URI facts.
  Every write is idempotent, so a retry after any failure is safe.
- **Then the listing refresh** (section 5): classify what the run wrote, and, only when the walk has reached the
  finalized head, publish. A publish is always preceded by a classification, so a classification that failed earlier
  heals at the next caught-up run instead of waiting for a registration that would remember it. A refresh failure is
  logged and never fails the run: the windows are already applied and the next run refreshes again. It shows only in
  the server log (the run is recorded as completed), so a Home block that does not appear after the last run means
  the log is the place to look.
- **Budget.** A run stops applying after 30 s of wall time or 20,000 accepted events, after the window in flight. The
  cursor moves only past windows that were fully applied. The event cap is what keeps a dense run short: every accepted
  registration is a row to classify afterwards.
- **Failure.** A failure after at least one window was applied stops the run early, keeps that progress, and logs the
  reason; the next run retries the failed window first, and a window that cannot make progress fails the run loudly. A
  failure before any progress fails the run and leaves the cursor untouched.

**Backfill, measured.** The verified raw logs served through a fake RPC (so no network time) into a scratch MySQL
under the shipped budget took 36 runs that read blocks plus one quiet confirming run, 837 s in all, each run 13 to 32 s
including the listing refresh (a real provider adds fetch time, about 3.4 s for a dense window). It ended with 373,567
registry rows, 375,498 ledger rows, and 6,619 directory entries published by the run that reached the head. The same
6,619 came out under a 60,000-event budget (19 runs, up to 69 s each) and a 30,000-event budget (27 runs, up to 57 s), so
the listing does not depend on how the walk is cut into runs. Every run is one operator click until the cursor reaches
the finalized head.

## 4. Where the data goes, and why not the directory table

Every registration is one row in `agent_directory_registry_rows`, which has the directory table's columns plus
`listing`:

| Column | Value |
|---|---|
| `externalKey` | `eip155:56:<registry>:<agentId>` (agent ids start at 0) |
| `registrant` | the `owner` the `Registered` event records, lowercase; a chain fact, not a verified operator |
| `displayName` | the name from inline registration JSON when it has one, else `Agent #<id>`; self-asserted, capped at 255 |
| `locatorHost` | the lowercased host of an https URI, as recorded |
| `profileUriHash` | SHA-256 hex of the full URI: equal for byte-identical registrations |
| `sourceSignalNote` | what the URI is (web link, IPFS reference, inline JSON, none, unrecognized scheme), that Nooscape did not fetch it, and that ownership is not verified; never the URI itself |
| `mintBlock`, `secondaryTransferCount`, `handoutCount`, `uriUpdateCount` | rolled up from the activity ledger onto the registry row, null until the walk has covered the agent |
| `listing` | where the row stands against the listing rules (section 5) |

The ledger is the existing EVM activity ledger (`agent_directory_chain_activity`): a `mint` per registration, a
`secondary` per change of hands, a `uri_update` per URIUpdated event. A `URIUpdated` event also updates the row's
`locatorHost` and `profileUriHash` to the new URI and puts the row back to pending; the display name stays as asserted
at registration, and the registrant and everything else are untouched.

**Why a separate table.** The first design wrote the 373,567 rows into `agent_directory_entries`. Measured on a copy
of that design at 613k rows (the 373,567 plus a 240k stand-in for the existing sources), every directory aggregate took
about 9.5 s against about 3.7 s at 240k (the figure `readCache.ts` already records), and a FULLTEXT search took 8.7 to
12 s even for a rare word, because the search ORs two FULLTEXT matches and scans. A one-word search such as "agent"
would also match about 370k placeholder names. A `listing` column on the directory table did not help: the planner
drives the aggregates from the source join and scans each source's rows anyway. So the directory table is untouched,
the registry rows live beside it with four composite indexes that make the listing rules index-only scans, and only the
listed rows are published into the directory. Search, the aggregates, and the funnel therefore read what they always
read, plus a few thousand rows.

## 5. The listing rules

A registration's `listing` is a pure function of recorded facts and published thresholds. It is recomputed, never
asserted:

| State | Meaning |
|---|---|
| 1 listed | passes every rule; published into the directory |
| 2 grouped | its exact profile link, its host, or its wallet is shared with many other registrations |
| 0 no link | no usable profile link: no URI, an unrecognized scheme, or inline JSON that did not parse (or exceeded 8 KiB) |
| 4 numeric name | the recorded name is only digits |
| 3 pending | written, not yet classified |

The thresholds (`BSC_LISTING_RULES` in `server/agentRegistryRows.ts`, printed on the Home page from the server so the
page and the rule cannot disagree):

- a profile link held by **2 or more** registrations is shared (the exact URI, byte for byte);
- a host that **50 or more** registrations point at is a platform host;
- a wallet that registered **10 or more** agents is a mass registrant;
- counts are over **every** registration of the source, held out or not (a wallet that registered 9 listed agents and
  a tenth with no link has registered 10, and all of them are grouped).

Measured against the 2026-10-13 snapshot: 17,988 have no usable link, 5,401 are named only with a number, 343,559 are
grouped, and **6,619 are listed**. Among the rows that have a link and a real name, the host rule alone holds out about
181k (the largest host group is 129,213 registrations), the wallet rule alone about 16k (the largest wallet registered
13,419), and sharing an exact link alone about 1.3k (the largest link is held by 126,300). Most of the rest trip several
rules. A rule on repeated names (20 or more) was measured and dropped: it held out only 94 more rows and needed an extra
index.

How the bars were chosen, and what moving them does (the listed count at the snapshot for each pair of bars; the
shared-link, no-link, and numeric-name rules apply throughout):

| Wallet bar \ host bar | 200 | 50 (shipped) | 20 |
|---|---|---|---|
| 10 (shipped) | 6,887 | **6,619** | 6,606 |
| 5 | 6,626 | 6,365 | 6,352 |
| 3 | 6,159 | 5,902 | 5,889 |
| 2 | 5,484 | 5,237 | 5,226 |

The host bar sits at 50 because three multi-tenant hosts hold 67 to 111 registrations each and the next host down holds
13; going from 50 to 20 moves 13 rows. The wallet bar is the real lever. A bar of 2 gets close to 5,000 but holds out
every developer who registered more than one agent (5,484 of the survivors come from wallets with a single
registration), which is a statement about the wallet, not about the agent. Tightening a bar later is automatic at the
next classification; loosening one needs the reviewed migration described below. That asymmetry is why the shipped
numbers are the principled ones (a mass registrant, a platform host) and not the ones that hit a round count.

These are statements about shared records, not about agents. A held-out registration is called shared, never fake, and
the Home page says Nooscape did not fetch any profile link. The listing is a filter on what the chain already says, not
a quality bar: a listed registration is one whose link, host, and wallet are not shared with many others.

**The listing follows the facts.** A listed row is grouped as soon as its group reaches a threshold (the next wallet
registration, the next registration on its host, a second registration of its link). A row that left a group through a
URIUpdated sends the rows it left behind back to pending when the group fell below its threshold. Both are covered by
tests against a real database.

**Publishing waits for a caught-up walk.** Group sizes are only complete once every registration up to the finalized
head has been read, and a row listed on a partial read could be grouped by the next window and flicker out of the
directory. So every run classifies, and only a run that reached the head publishes: it inserts listed rows missing from
the directory (in chunks of 2,000), refreshes the profile link and chain rollups of listed rows that changed, and removes
rows that are held out. A row that is pending again keeps its entry until classification decides, so two overlapping
runs cannot delete a row the other is about to relist. Nothing an operator set on a directory row (`hidden`) is ever
touched, and it survives a removal: the flag is copied onto the registry row first, so a registration that leaves the
listing and comes back returns hidden.

**Loosening a threshold does not promote rows already grouped.** The classification re-evaluates pending and listed
rows only, which keeps a steady-state refresh to a few seconds. Changing a threshold is a code change plus a reviewed
migration that sends grouped rows back to pending (`UPDATE agent_directory_registry_rows SET listing = 3 WHERE
listing = 2`); the next refresh reclassifies them.

## 6. Public surfaces

- **Directory, search, counts, funnel.** They read `agent_directory_entries`, so they see only the listed registrations.
  The funnel's mint step counts measured mints across both EVM registries; the What-changed readers stay Robinhood-only.
- **Home.** The total, the registry headline, and the locator-listing count keep their meaning: listed BNB Chain
  registrations are counted on their own line, never as locator listings. A "BNB Chain ERC-8004 registry" block shows
  the registrations on-chain, how many are listed, how many are held out and why (shared, no usable link, numeric
  name), the profile links and hosts shared by the most registrations, and the rules. The block appears only after a
  walk that reached the finalized head has published: before that the stored count is a partial read of the chain and
  "registrations on-chain" would be wrong. Shared-link labels come from self-asserted names, so they are cleaned like
  every directory name (no control, bidirectional, or zero-width characters) and capped.
- **Live population card.** It leads with the acknowledged total and shows the reviewed subset beside it ("240,175
  acknowledged, 82 reviewed on 2026-10-13"). Protocol population and Discovery surfaces cover every protocol Nooscape
  reads (Catalog, Solana SAID, ERC-8004 on Robinhood Chain, Solana registry, Solana 8004, A2A, and BNB Chain once it is
  listed): the acknowledged count first and the reviewed count beside it, one protocol per reviewed record so they add
  up to the reviewed total. The two ERC-8004 registries are the same contract on two chains, so each is named by its
  chain wherever a protocol is shown (the card, search hits, the agent page).
- **Home map (2026-10-15, replaced by PR-B3).** `liveData.mapAcknowledged` returns a fixed sample of at most 30 of the listed
  registrations (the ids that hash lowest) and how many are listed in all. Until PR-B3 the map drew them as hollow squares
  beside the reviewed records, counted them apart ("BNB Chain · 30 of 6,839 acknowledged"), and gave each a card that said it
  was acknowledged, not reviewed, with no tier and no evidence (docs/approvals/2026-10-15-informational-use-and-bnb-map.md).
  The page no longer asks for the sample: BNB Chain is on the map only as groups of registrations (`liveData.mapFleets`).
  The endpoint is still there.
- **Agent page.** The wallet and host look-alike counts for a BNB Chain registration are counted over the whole
  registry, listed or not, and say so, because most of a wallet's other registrations are held out.
- Held-out registrations are stored and queryable by wallet (`agent_registry_rows_registrant_idx`); a public lookup by
  wallet is not built yet.

## 7. Provider and secrets

The provider is NodeReal. The endpoint URL **carries the account key in its path**, so it lives only in the
`BSC_RPC_URL` environment variable and never in the database, a source row, an error, a log line, or a run record:

- The source row records only the provider host (`https://bsc-mainnet.nodereal.io`, hostname `bsc-mainnet.nodereal.io`).
- The pass refuses to run unless `BSC_RPC_URL` is set, https, free of userinfo, and its host is exactly the approved
  one, so changing the variable cannot point the pass at a host nobody approved.
- Every error the client can throw is a fixed string built from the method name and an HTTP status. Any
  provider-supplied text is scrubbed of long token-like runs and capped at 200 characters. Tests plant a recognizable
  key and assert it appears in no message, including network failures whose underlying error carries it.

## 8. What the pass deliberately does not do

- No scoring, tiers, or quality judgments (D1): no A, B, C letters, no client-quality score, no token-risk overlay. The
  listing counts shared records; it does not rate an agent. The published census report keeps to this: it applies no
  junk filter and names no host (section 12).
- No URI fetching (D2) by this pass, in the worker or anywhere else. Reversed in part on 2026-10-15, for informational
  use only: see docs/approvals/2026-10-15-informational-use-and-bnb-map.md. This pass still fetches nothing. A one-off
  census on 2026-10-16, run by a separate tool (bsc-b1-measurement-2026-10-16.md), did fetch registration files and
  agent addresses, and the entry note says so (section 12).
- No reputation or validation registry. The reputation ledger for BSC is a later phase and a separate source. (PR-B4 reads the reputation registry's feedback for an internal rater check only: bsc-rater-credibility-2026-10-16.md.)
- No hand-out narrative on the public surfaces yet. The rollup stores a hand-out count with BSC's own mint hour (8,000
  blocks at the measured 0.450 s per block), but nothing public reads it for BSC.
- No scheduled run. The scheduled flip is a separate reviewed migration after a clean attended period.

## 10. Known limits

1. **The listing is not a verdict.** It cannot tell a real agent from a copy that happens to have its own link, host,
   and wallet, because nothing is fetched. A registration with a link of its own on a quiet host and a new wallet is
   listed whether or not anything answers at that link.
2. **A wallet that registers many agents is held out wholesale**, including a developer who registered 10 real agents
   from one wallet. The threshold is a published number, not a judgment; lowering the bar means a reviewed migration.
3. **Anyone can hold a registration out by sharing.** Registering a copy of a listed registration's exact link
   from any wallet groups both, and the original's entry is removed at the next publish; registering 50 URIs on a host
   holds out every listed registration on it. The cost is one transaction for the copy and 50 for a host, the facts
   stay in the registry rows, and the listing is a default view, not a trust signal, but a held-out registration has
   no public page and there is no public wallet lookup yet. The same strictness hides both registrations when a
   developer registers one link twice. A fix that keeps the listing small: list only the earliest registration of a
   shared link (a copy is later) and treat the larger groups as templates. At the snapshot that lists 456 more
   registrations (6,619 becomes about 7,075), because most of the earliest members of shared links also trip the
   host or wallet bars. It was not made the default because the instruction was to filter hard; it is a decision to
   take if copies of listed links start appearing.
4. **The Robinhood activity readers are scoped to Robinhood**, so a BSC ledger does not leak into their totals; a BSC
   section of What-changed does not exist yet.
5. **Names for https URIs are placeholders** (`Agent #<id>`), by design: resolving them would need fetching (D2).
6. **A `URIUpdated` event does not refresh the display name.** It is the name asserted at registration.
7. **Database growth.** 373,567 registry rows (332 MB of data and 273 MB of indexes on the benchmark instance, 605 MB), 375,498
   ledger rows (174 MB and 162 MB, 336 MB, the same as before this change), and 6,619 directory rows (2.7% of the
   existing table). Read cost: with a 240k-row stand-in for the other sources plus the 6,619 published rows, the directory
   aggregates took 1.0 to 1.7 s each on the benchmark instance (about 9.5 s when the 373k rows lived in the directory
   table), an entry page 13 to 28 ms, and the registry profile 1.3 s uncached (cached for 30 s). Search kept the cost it
   has at that size. The ledger could be kept for listed registrations only later if storage matters.
8. **Cadence.** Once scheduled the source competes for the two-sources-per-tick limit; see the cadence note in the
   2026-10-13 handoff.

## 11. Rollout

1. Merge. Migration `0034` creates the registry rows table at boot (an idempotent `CREATE TABLE`, nothing to rebuild).
2. `BSC_RPC_URL` must be set in the Hostinger environment to the NodeReal endpoint (the operator added a NodeReal key on
   2026-10-13; confirm the variable is named exactly `BSC_RPC_URL` and holds the full URL, not the bare key).
3. On /admin/sources: **Stage BNB Chain ERC-8004 registry**, approve it, and press **Run chain pass** until the cursor
   reaches the finalized head. Nothing reaches the directory until the last run catches up and publishes. A press that
   fails names its cause in the console (an unset or mistyped `BSC_RPC_URL`, a provider refusal such as HTTP 401, a
   failed host check, or a rejected chain response), and the source row keeps the last error under its failed-run count.
   A failed run leaves the cursor where it was, so fix the cause and press again.
4. Compare the registrations on-chain shown on Home (373,567 at the 2026-10-13 snapshot, a few hundred more a day) with
   the chain, and read the listed count against the rules above.
5. Migration `0035` flips it to the scheduler (the 0021, 0027, and 0031 pattern): a 15-minute cadence, which in practice
   is one run about every 30 minutes, so the ~35 runs after the first attended one were estimated at about 17 hours. Measured pace on 2026-10-14 was a run every 30 to 45 minutes (the worker's eight slots an hour are fully used, see worker-operations.md), so expect 15 to 25 hours. The operator asked
   for it straight after the first attended run (2026-10-14, which succeeded at 03:01Z) instead of after a longer attended
   period, so the run that reaches the finalized head publishes the listing without a human in the loop. To review before
   that, pause the source on /admin/sources; nothing is lost, and Resume continues from the stored cursor. A failed run
   keeps its cursor and the next tick retries, and `verify-live.mjs` already holds this source to a 3-hour freshness limit
   once it is scheduled.

## 12. PR-B5 and the census report (2026-10-17)

**PR-B5, the gate change that would promote BNB entries into the reviewed census, is closed.** The operator decided on
2026-10-17 not to reverse "informational only" for BNB. BNB entries stay acknowledged and not reviewed, nothing is
promoted, no BNB entry touches the reviewed counts or the hero number, and gates G3 and G5 and the promotion migration
are not built. The operator's answers on how a promotion would work if B5 ever reopened are on record, marked as
applying only then: a human queue, G3 required, Tier 3 and nothing new, automatic demotion that only removes light, and a
daily BNB endpoint job that has run for at least a week first. Nothing reads them today.

**A census report is published under informational use.** `/field/bnb-registry-2026-10-16` reports the first census run
(bsc-b1-measurement-2026-10-16.md) as a dated aggregate: a funnel of counts, three findings and what the run does not
show. It lists no agent, ranks nothing, gives no score, names no host, and does not use the junk filter (D1 stands). Its
figures are in one data file with their sources, and a test holds the page to it. The run was a separate tool, not this
pass, so the pass still fetches nothing. The run fetched registration files and agent addresses, which the BNB entry
note, the home page's BNB card and the `/checker` page now say; its deviation from the 2026-10-15 bounds (read sizes of
64 KiB and 256 KiB against a 4 KiB probe cap, and a user-agent page that did not yet describe it) is logged in
[approvals/2026-10-17-bnb-census-report-and-b5-closed.md](./approvals/2026-10-17-bnb-census-report-and-b5-closed.md).
Any later pass stays inside the 2026-10-15 limits unless the operator amends them in writing.

**Decided on 2026-10-17:** the endpoint-host rule is stored by the production clustering, in a table of its own
(`bsc_endpoint_host_groups`, migration 0040, with the rule's version and date on each row). It draws no light, changes no
entry's G1 result and changes no count the public reads; a light needs a separate decision. The report keeps its measured
numbers. **On hold:** a "what we observed" block on each BNB entry page. Nothing is built until the report has been live and
the operator has shown the draft to a few outsiders.
