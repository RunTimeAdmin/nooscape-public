# The watchlist and the webhook for Arc

Server code and the document. No migration, no new table and no new setting: the watchlist, the webhook and the pass are [stage D5](./data-access-2026-10-19.md) as they were, and this changes which chains they know.

**Status.** Shipped in PR 178 on 2026-10-20, after the Owl's Catch.

**Decided:** 2026-10-20, by the operator, in chat: "Owl's Catch, watchlist, claims are good to add   lets finish the ARC arc so to say". The stage 3 record of the multichain work had kept every extra chain out of the watchlist and the webhook on purpose ("the brief puts events for the new chains out of scope"), and the operator has now asked for the opposite for Arc.

## What changes

A Builder or Pro key can watch an agent on Arc, and the key's webhook hears about it, while `chain_arc` is on.

- **Watching.** `POST /api/v1/watches` takes `chain: "arc"` with the registry token id, as it takes `bnb`. It finds the listing the way every lookup does, through the public view, so an Arc registration that the listing rules hold out is "not found" and one that is listed can be watched. The answer for a chain that is not served names the chains that are: "chain must be one of robinhood, bnb, solana, arc" with Arc on, and the three as before with it off.
- **The list.** `GET /api/v1/watches` names the chain of each watched agent from the chains served now, so an Arc watch reads `chain: "arc"` with its token id while the switch is on. With it off the key still has the watch and can remove it, and the list gives no chain and no agent id for it (the schema allows both to be null), as it does for any listing the API cannot name.
- **The events.** For an Arc listing the pass writes the events it writes for any EVM listing: `ownership.changed` (a transfer from the registry's ledger, with its block, transaction and hand-out flag), `claim.changed` (when Arc claims exist) and `listing.removed` and `listing.restored`. `feedback.added` and `feedback.revoked` are Robinhood Chain's alone, because the public API gives rating counts for no other chain, so Arc has none. An event names the agent as the API does: `chain: "arc"`, its token id, `erc8004_arc`, its page and its API address.
- **The document.** The OpenAPI document's chain lists for the watchlist (the add request and the list's `chain`) gain Arc with the other lists, and are the original three while every switch is off. The developer page says the watchlist and the webhook cover the extra chains that are on.
- **Ethereum and Base come with it.** The change is for every chain the API serves, not for Arc alone, so a key can watch an agent on Ethereum or Base when their switches are on. Their events are Arc's, with their own mint hour. Held by tests from 2026-10-28 ([the record](./base-ethereum-catch-watch-2026-10-28.md)).

## A hand-out is judged by the chain's own mint hour

An `ownership.changed` event carries `is_handout`: a transfer from the minting wallet inside the first hour after the mint, which the API calls a platform hand-out and not a sale. The pass measured "the first hour" in Robinhood Chain's blocks (36,000) for every EVM listing. The public API's own `registry_events` already uses each chain's number (Arc 7,080, BNB Chain 8,000), so the two could disagree. The pass now uses the chain's number too, so the webhook's flag and the API's agree for Arc, and for BNB Chain, whose events were classified with Robinhood's longer window until now. This is the one change that reaches the chains that were already served: for a BNB Chain listing, a transfer from the minting wallet between 8,000 and 36,000 blocks after the mint was flagged `is_handout: true` and now is not.

## While the switch is off

- **Nothing is said about an Arc listing**, not even that it left the public view. The pass skips a listing on a chain the API does not serve now, and does not record its change of view either, so when Arc is switched on again no event claims a return that was never reported as a departure.
- **A watch made while Arc was on is kept.** The key can list it and remove it, and the list names no chain, no agent id and no registry for it while Arc is off. Nothing is written for it until the chain is served again.
- A fact the pass reads again for its overlap (fifteen minutes of ledger rows, a hundred claim numbers) can be reported once the chain is served again, as any late row is: events are sent at least once and may arrive late.

## Held by a test

- `apiWebhooks.test.ts` (through the real router): adding an Arc agent only while the switch is on, with each refusal's words and the list of chains it names, the answer held to the document with Arc in it, the list naming Arc while it is on and no chain once it is off, and the watch still removable.
- `webhookPass.test.ts`: an Arc listing's ownership and claim events in Arc's name, nothing for it with the switch off and no record of a change of view, and `listing.removed` and `listing.restored` while it is on.
- `webhookStore.integration.test.ts` (real MySQL, with migration 0046 pasted): the hand-out flag for Arc (inside 7,080 blocks and outside), BNB Chain (inside 8,000 and outside) and Robinhood Chain (inside 36,000 and outside).
- `apiV1Chains.test.ts`: the watchlist's lists in the document gain the chain with the others and are the original three with every switch off, and both files ask which chains are served.
- Each guard was broken once to confirm a test fails: the pass naming agents among the original three only (three tests fail), the watchlist accepting the original three only (two), the hand-out window being Robinhood's for every chain (one) and a listing on a chain not served being tracked (one).

## A gap that was there before and now reaches more chains

The independent review of this change found it, and it is not changed here because it needs a migration. A watch holds the id of a directory entry. When the listing rules hold a registration out, the pass deletes its entry from the directory, and when it is listed again it gets a new id. So a key that watches an agent on BNB Chain (or now Arc, Ethereum or Base) never hears `listing.removed` when the rules hold it out, and its watch does not follow the agent back when it is listed again, though the API's own text says a listing that leaves stays on the list and an event says so. The fix is to keep the chain and the registry key on the watch row and resolve the watch by that key (a migration and a change to the pass), or to keep entry ids stable across hold-out and re-listing. Arc's listing rules are provisional and may be tuned after the census, so the gap will show first on Arc and then, once its first pass publishes, on Base. It is todo item 125.

## Not here

- **Webhooks are still the operator's to turn on**: until `WEBHOOK_SIGNING_KEY` is set and the tables and the cron job exist, the API answers 503 for the watchlist and the webhook, as before.
- **Events for Arc ratings.** Arc has no ratings read, so there is nothing to tell.
