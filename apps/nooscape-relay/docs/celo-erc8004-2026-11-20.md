Status: **BUILT AND TESTED (2026-11-20); SWITCHED OFF; NOT STAGED.** The operator picked Celo on 2026-11-20 from the chain list of the 2026-11-19 review, whose line said it works on public nodes. Celo runs the same contract as Ethereum, Monad and Gnosis, and its official public node answers the whole history, so the chain needs no key ([the Gnosis record](./gnosis-erc8004-2026-11-06.md) is the model). ## 2. What the real chain held (read on 2026-11-20)

- **The same contract.** The identity registry at `0x8004A169FB4a3325136EB29fA0ceB6D2e539a432` is the same 130-byte proxy as on every chain, and its implementation, `0x7274e874ca62410a93bd8bf61c69d8045e399c02`, has the same 14,474 bytes of code as Ethereum's, so the decoding is shared. The reputation and validation registries are there too, as the same proxies with the same implementations as on the other chains ([the registry tripwire](./registry-tripwire-2026-11-20.md) watches all three). Celo's validation registry has the most traffic of any chain ([the census](./validation-registry-census-2026-11-20.md)).
- **Where it starts.** Deployed at block 58,396,724 (2026-02-05 13:18:02 UTC), found by binary search on `eth_getCode` (24 probes; empty at 58,396,723, 130 bytes at 58,396,724) on two public nodes that serve state that far back and agree: `forno.celo.org` (the Celo Foundation's) and `celo.gateway.tenderly.co`. The first registration is at block 58,399,999 (14:12:37 UTC the same day). The head was 83,293,113 on the day, so 24,896,389 blocks lie between the deploy block and it. The `finalized` tag is served (1,403 blocks, about 23 minutes, behind the latest).
- **How fast it moves.** 1.0000 s a block over the last 100,000 blocks, so an hour is 3,600 blocks.
- **What it holds.** 10,078 registrations, ids 0 to 10,077 (counted from the events; `ownerOf` finds the same highest id). 8004scan lists 9,948. The three kinds of event the pass asks for number 30,323: 10,078 `Registered`, 10,154 `Transfer` (10,078 mints and 76 hand-overs, none to the zero address) and 10,091 `URIUpdated` (on 7,382 agents).
- **When.** The rush was in March and April: registrations by month were 333 (from 5 February), 5,847, 2,867, 149, 461, 94, 50, 70, 141 and 66 (to 20 November). The busiest day was 2026-03-21 with 393. The last 30 days hold 94, about three a day. The newest registration was made on the day, at 16:22 UTC.
- **What the nodes allow** (`eth_getLogs`, read 2026-11-20). `forno.celo.org` answers at most **5,000 blocks** a call and refuses a wider window with an HTTP 400 whose body is JSON-RPC error -32602, "query exceeds range, retry smaller (max block range 5000, got N)", which the client reads as a block-range fault. It puts no cap on the response: 300 consecutive windows of 5,000 blocks in the densest stretch (1.5 million blocks, 11,256 logs, 42.3 MB) took 79 s with three at a time, and none was refused (median 643 ms, 95th percentile 1.5 s, longest 1.9 s). The Tenderly public gateway answers windows of about 3,000,000 blocks (8,237 logs, 14.9 MB in 1.9 s) and refuses 10,000,000, but it is not the chain's own node. The operator's Alchemy account does not have Celo enabled ("CELO_MAINNET is not enabled for this app"), so the plan the Base, Monad and Gnosis passes use is not an option until the operator turns the network on.
- **The three kinds, by window.** Cut into windows of 5,000 blocks from the deploy block, the history is 4,980 windows, 1,675 of which hold an event. The busiest holds 471 events (388,674 bytes as JSON); the largest is 461,070 bytes (263 events). An event is 3.3 kB on average as stored, and 3.8 kB in the node's answers, because most links are inline documents (section 3).

## 5. The rehearsal

The real pass, with the budget in the entry, against a scratch MariaDB 10.11 and the real chain through the official node, from the deploy block to the finalized head, the way the operator's "Run chain pass" button will. The script is scratch and is not committed.

- 48 runs, 1,417 seconds of runs in all (24 minutes), the longest 33.7 s. 47 of them moved the cursor, and the 48th found nothing. The 30 s clock ended most runs, so they read between 42 and 200 windows: four used all 200, and one, in the dense stretch, ended on the 5,000-event bound. The walk was the 4,980 windows of the offline count, in 5,191 requests, and no run failed.
- 30,325 events accepted: the 30,323 of section 2 and the two of one registration made while the walk ran.
- 10,079 registry rows stored (none past the flood cap: no host has more than 261), and in the ledger 10,079 mints, 76 hand-overs and 10,091 URI updates. About 38 MB of tables in all (registry rows 19.5, ledger 18.1, entries 0.1), and a process that stayed under 133 MB.
- **517 entries published**, of 10,079 registrations (5.1%), against 1.0% for Gnosis and 1.4% for Monad. 9,364 rows were grouped and 198 have no usable link (an empty link, a compressed one, a plain http link or raw text). The two large wallets alone account for 8,564 of the grouped rows. Of the 517, 287 are named `Agent #n` (the link carries no name) and 150 have a host. None is hidden.
- The first pass is about fifty presses of the button (a scripted loop through the admin API, as for Gnosis, takes about 25 minutes), or the scheduler's own ticks if the source is flipped first.

## 6. The operator's steps

Production runs on its own server; its database is the `db` container of its stack.

0. **Read the migration log.** Version 60 must not be recorded (on 2026-11-20 the newest was 59, `0059_catalog_party_host.sql`, and 60 rows were recorded); if it is, say so and the number changes (a version already recorded is skipped, which once lost migration 0047).
1. **Migration 0060, by hand, at a quiet moment** (not on a worker tick: :00, :15, :30, :45). It appends `erc8004_celo` to the protocol list of four tables. It needs 0046, 0051, 0053 and 0057, which production has, because every statement restates the whole list.
   - Check first: each of the four columns must already end with `'erc8004_monad','erc8004_gnosis')` (production's `ingestion_sources.protocol` did on 2026-11-20).
   - Apply `drizzle/0060_celo_erc8004_protocol.sql` (the four statements, with `--> statement-breakpoint` markers between them to remove if the console does not take them). Check again: each now ends with `'erc8004_gnosis','erc8004_celo')`.
   - Record it: `INSERT INTO nooscape_schema_migrations (version, name) VALUES (60, '0060_celo_erc8004_protocol.sql');`. The name must be exactly the file's: a version recorded under another name stops the next boot.
   - Rollback is the same four statements with the earlier list (the one the first check shows), then deleting version 60 from the log. MySQL cannot drop a value a row still holds, so first count the rows that carry `erc8004_celo` in the four tables; every count must be 0.
   - Staging the source before the file is applied answers "The database does not have the Celo protocol value yet. Paste migration 0060 first", and creates nothing.
2. **Set `CELO_RPC_URL=https://forno.celo.org`** in `app.env` on the server. The address holds no key. The pass accepts only the host `forno.celo.org`.
3. **Add `chain_celo` to `VITE_FEATURES`** in the stack's `.env`, keeping the value it has, and deploy (`bash deploy.sh $(cat .deployed)`, because the list is read when the site is built).
4. **On /admin/sources**: Stage Celo ERC-8004 registry, approve it, press Run chain pass until the run that follows one that moved the cursor finds nothing.

Rollback of the whole change: remove `chain_celo` from `VITE_FEATURES` and deploy. Celo then disappears from every read, and the source can be paused.

## 10. The scheduled flip (migration 0061)

The source `celo-erc8004-identity-registry` has been `manual_only` since the go-live, so nothing reads the registry's new registrations and the chain's figures stay as of the last manual pass (19:03Z on 2026-11-20). Migration 0061 hands it to the scheduler once a day, the way 0050 did for Arc, 0052 for Ethereum, 0054 for Monad and 0058 for Gnosis. The operator asked for it on 2026-11-20 ("all in order", where the daily run came first).

- **What it is.** One guarded UPDATE that names no protocol, applied at boot like 0050, 0052, 0054 and 0058. It changes the source only if it is the approved Celo source by its key, active, still `manual_only`, holding a `celo:` cursor, with a recorded success and no recorded failure. Then it sets `scheduled`, 1440 minutes, due now. Run again, or on a database where the source is not in that state, it changes nothing. `server/celoScheduledFlip.test.ts` tests each guard against a real MySQL (and MariaDB 10.11), including that it names no protocol and that a source with a key close to the approved one and a Celo cursor is left alone. Thirteen planted changes to the file and to the two freshness lists were run, and all thirteen were caught.
- **What the pass reads.** The pass itself is unchanged: chain facts from finalized blocks through the Celo Foundation's public node (`CELO_RPC_URL`, `forno.celo.org`, no key), windows of at most 5,000 blocks, up to three at a time, a run bounded to 200 windows, 30 seconds and 5,000 events, no URI fetched and no reviewed record added. A day of Celo is 86,400 blocks (one second a block), 18 windows. The registry is nearly still: 94 registrations in the 30 days to 2026-11-20 (about three a day), against 30,323 events of the three kinds in all and 471 in the busiest window. One run a day has room, and if Celo ever records more than 5,000 events a day the cadence has to shorten. The pass does not start while the `chain_celo` switch is off.
- **At the deploy.** The migration runs at the first boot, the source is due at once, and the worker's next ticks (every 15 minutes) claim it; the worker takes at most two due sources a tick, so a freshly flipped source can wait two or three ticks. The first run reads from the stored cursor, where the last manual pass stopped (the finalized block 83,299,336 at 19:03Z on 2026-11-20), to the finalized head. The next is due a day after it finishes. Deploy it only after the first walk has caught up, which it has: the migration cannot tell a cursor at the head from one part of the way, and a source flipped part of the way would read 200 windows a day.
- **The live check.** `scripts/verify-live.mjs` gets `erc8004_celo: 36`, so a scheduled Celo source that has not succeeded within 36 hours fails the check. The status page keeps a copy of the limits (`client/src/lib/statusModel.ts`), and a test holds it equal to the script's, so it gets the same line. Between the deploy and the end of the first run the source still shows its old success, so run the check again after the first tick.
- **What changes on the site.** The Celo tab's "Last successful read of this chain" moves each day, and a registration that appears is listed, under the listing rules, within a day. Nothing else changes.
- **The migration number.** The boot runner refuses to start when a version is recorded under another file's name, so the number was checked against production's migration log on 2026-11-20, read over ssh: versions 60 down to 57 recorded under the same file names as the repo (60 is `0060_celo_erc8004_protocol.sql`, applied at 18:26Z), 61 rows in all, and nothing at 61. No other pull request was open.
- **Rolling back.** Set the source back to operator-paced with `UPDATE ingestion_sources SET executionPolicy = 'manual_only' WHERE sourceKey = 'celo-erc8004-identity-registry';`. The cursor is not touched.
- **Chosen by Claude, so the operator can say no.** Once a day, as Arc's (until 2 November), Ethereum's, Monad's and Gnosis's are, and the 36-hour allowance the other daily sources get.


## 11. The census report

Stage 4 of the six the operator ordered with "all in order". The 15 read-only queries of the other chains' censuses were run on production on 2026-11-20 at 19:44 UTC, after the registry pass that finished at 19:03 UTC, and every row they returned is in [the measurement](./celo-census-2026-11-20.md); the queries are in [one file](./celo-census-queries-2026-11-20.sql). The report is `/field/celo-registry-2026-11-20`, behind `chain_celo`, with a Today block.

- **What the registry holds.** 10,080 registrations stored and counted, none hidden, none past a host's cap, 517 listed (5.1%).
